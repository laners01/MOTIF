# 필요한 키 이름만 알리는 예시다. 실제 값은 절대 커밋하지 않는다.
#
# 확장자가 .txt 인 이유: .yaml 이면 `kubectl apply -f infra/k8s/40-core-api/`
# 로 디렉터리를 적용할 때 이 파일까지 적용되어 실제 Secret 을 자리표시자
# 값으로 덮어쓴다. (Postgres 에서 실제로 겪은 사고다.)
#
# ── 여기 있는 키는 전부 fallback 이 없다 ────────────────────────────────────
# application-prod.yml 이 `${KEY}` 로만 참조한다. 하나라도 빠지면 파드가
# 기동하지 않는다 — 조용히 기본값으로 뜨는 사고를 막기 위한 의도된 설계다.
# **키를 추가하는 앱 변경은 이 파일과 실제 Secret 을 같은 날 함께 고친다.**
#
# ── 값의 출처 ───────────────────────────────────────────────────────────────
# 옮겨오는 값 (새로 만들지 않는다. 이미 서버에 있는 계정의 것을 그대로 쓴다):
#   DB_PASSWORD      : postgres-secret 의 CORE_APP_PASSWORD (계정 core_app)
#   MQ_PASSWORD      : rabbitmq-secret 의 RABBITMQ_CORE_PASSWORD
#                      (계정 core-api, vhost /motif)
#   REDIS_PASSWORD   : redis-secret 의 비밀번호
#
# 새로 만드는 값:
#   JWT_SECRET       : 팬 앱 토큰 서명키
#   ADMIN_JWT_SECRET : 어드민 토큰 서명키 — **JWT_SECRET 과 반드시 다른 값**
#                      (어드민 명세 §1.2). 같은 키면 팬 토큰 서명이 어드민
#                      경로에서도 통과하고, typ 클레임 하나만 남는다.
#
# 사람이 정하는 값:
#   GOOGLE_CLIENT_ID : 비밀은 아니지만 환경마다 다르다. 틀린 aud 는 다른 앱의
#                      토큰을 통과시키는 구멍이라 fallback 을 두지 않았다.
#
# ── AWS 키 (2026-09-14 추가) ────────────────────────────────────────────────
#   AWS_ACCESS_KEY_ID / AWS_SECRET_ACCESS_KEY
#
# 이 둘만 다른 키들과 성격이 다르다 — **application.yml 이 참조하지 않는다.**
# AWS SDK 가 환경변수에서 직접 읽으므로 빠져도 파드는 정상 기동한다. 그래서
# 빠진 것이 S3 를 칠 때에야 AccessDenied 로 드러난다.
#
# 왜 필요한가: 운영 서버는 Lightsail 이고 IMDS 가 `AmazonLightsailInstanceRole`
# 의 임시 자격증명(ASIA…)을 흘린다. 그건 **SSAFY 계정** 것이고 motif-media 버킷은
# **우리 계정**에 있다 — 크로스 계정이라 서명은 되는데 S3 가 거부한다. 그 역할은
# 남의 계정이라 고칠 수도 없다. SDK 자격증명 체인에서 환경변수가 IMDS 보다
# 앞이라는 점을 이용해 우리 계정 키로 덮어쓴다.
#
# 값의 출처: 우리 AWS 계정 IAM 사용자 `motif-core-api` 의 액세스 키.
# 그 사용자에 붙는 인라인 정책(3개 다 필요하다):
#
#   {"Effect":"Allow","Action":["s3:PutObject","s3:GetObject"],
#    "Resource":"arn:aws:s3:::motif-media/*"},
#   {"Effect":"Allow","Action":["s3:ListBucket"],
#    "Resource":"arn:aws:s3:::motif-media"}
#
#   - GetObject 가 없으면 업로드는 되는데 등록 시 HEAD 확인이 막힌다
#   - ListBucket 의 Resource 에 `/*` 를 붙이면 조용히 무효다(버킷 단위 액션이다)
#
# 확인: `kubectl exec deploy/core-api -- printenv AWS_ACCESS_KEY_ID`
#       patch 만 하고 rollout restart 를 빠뜨리면 반영되지 않는다.
#
# ── CloudFront 서명키 (2026-09-15 추가) ────────────────────────────────────
#   CLOUDFRONT_PRIVATE_KEY
#
# 보호 등급 미디어(모티프 결과물·본인 PRIVATE 영상·게시 전 프리뷰)의 signed URL
# 발급에 쓴다 (API 명세 §1.7). **이 키가 새면 전 보호 콘텐츠의 서명을 위조할 수
# 있다** — 단일 실패점이므로 팀 비밀 저장소와 이 Secret 말고 어디에도 두지 않는다.
#
# **이 키도 빠져도 파드는 뜬다.** AWS 키와 같은 성격이다 — application.yml 이
# `${CLOUDFRONT_PRIVATE_KEY:}` 로 빈 기본값을 둔다. 로컬·CI 가 보호 미디어를
# 건드리지 않고 기동하게 하려는 선택이고, 운영에서 빠지면 파드는 1/1 Ready 인 채
# 보호 등급 URL 발급만 IllegalStateException 으로 실패한다(fail-closed —
# 무서명 URL 이 새어 나가지는 않는다).
#
# `CLOUDFRONT_KEY_PAIR_ID` 는 **여기 넣지 않는다.** 서명된 URL 의 쿼리에 그대로
# 실려 나가는 공개 식별자라 비밀이 아니고, application.yml 이 기본값으로 들고 있다
# (`motif.media.signing.key-pair-id`). 배포가 바뀌면 그 값을 고친다.
#
# 값의 출처: CloudFront → Key management → Public keys 에 등록한 공개키와 짝인
# RSA 개인키. 오프라인에서 만든다:
#
#   openssl genrsa -out cf_private.pem 2048
#   openssl rsa -pubout -in cf_private.pem -out cf_public.pem   # 콘솔에 붙여넣을 공개키
#
# **PKCS#8 이어야 한다.** openssl 3.x 의 genrsa 는 PKCS#8 을 낸다(`BEGIN PRIVATE KEY`).
# 1.x 는 PKCS#1(`BEGIN RSA PRIVATE KEY`)을 내는데 Java KeyFactory 가 못 읽는다.
# 확인: `head -1 cf_private.pem` 가 `-----BEGIN PRIVATE KEY-----` 여야 한다.
# 아니면: `openssl pkcs8 -topk8 -nocrypt -in cf_private.pem -out cf_private_pkcs8.pem`
#
# ── 워커 콜백 토큰 (2026-09-19 추가) ───────────────────────────────────────
#   MOTIF_WORKER_TOKEN
#
# AI(GCP Cloud Run Job)가 합성 결과를 돌려줄 때 싣는 공유 비밀이다
# (S15P21D104-536, AI 서버 명세 §3.3·§3.4). 접수 호출(우리 → AI)에도 같은 값이
# 실린다 — 양방향이 비밀 하나를 공유한다.
#
#   POST /api/worker/v1/composite-jobs/{uuid}/done
#   X-Motif-Worker-Token: <이 값>
#
# **JWT 가 아닌 이유.** 상대가 우리 사용자도 어드민도 아니라 토큰을 발급·갱신할
# 주체가 없다. 비밀 하나를 양쪽 Secret 에 두고 대조한다(WorkerTokenFilter 가
# MessageDigest.isEqual 로 비교한다 — String.equals 는 타이밍이 샌다).
#
# **이 키도 빠져도 파드는 뜬다.** CLOUDFRONT_PRIVATE_KEY 와 같은 성격이고
# application.yml 이 `${MOTIF_WORKER_TOKEN:}` 로 빈 기본값을 둔다. 다만 비어 있으면
# **콜백이 전부 401 이다**(fail-closed) — 빈 값을 "검사 생략" 으로 읽으면 설정 실수
# 하나로 콜백이 인터넷에 열리고, 아무나 남의 잡을 DONE 으로 바꾸거나 FAILED 로
# 닫을 수 있다. 조용히 열리는 쪽으로 기울지 않는다.
#
# 값의 출처: 새로 만든다. 32바이트 이상 난수.
#
#   kubectl patch secret core-api-secret --type merge \
#     -p "{\"stringData\":{\"MOTIF_WORKER_TOKEN\":\"$(openssl rand -hex 32)\"}}"
#   kubectl rollout restart deployment/core-api
#
# **같은 값을 AI 팀 Secret Manager 에도 넣어야 한다.** 한쪽만 회전하면 콜백이 전량
# 401 이 되는데, 그 401 은 "토큰이 틀렸다" 로 보여 비밀이 샌 것으로 오해하기 쉽다.
#
# ── 주입 (여러 줄 PEM 이라 stringData 로 넣지 않는다) ──────────────────────
# `--from-literal` 이나 stringData 에 넣으면 줄바꿈 이스케이프에서 깨지기 쉽다.
# base64 로 data 에 바로 넣으면 그 문제가 없다.
#
# **파일이 있는지 먼저 본다.** 없으면 `$(base64 < 없는파일)` 이 빈 문자열이 되고,
# patch 는 그대로 성공한다 — `secret/core-api-secret patched` 가 찍히는데 값은 비어
# 있다. 2026-09-15 에 실제로 밟았다(키를 만든 곳은 개발자 PC, patch 는 서버였다).
#
#   head -1 cf_private.pem && base64 -w0 < cf_private.pem | wc -c
#   → -----BEGIN PRIVATE KEY-----
#   → 2272        (2048비트 PKCS#8 기준. 0 이나 오류면 여기서 멈춘다)
#
#   kubectl patch secret core-api-secret --type=json \
#     -p="[{\"op\":\"add\",\"path\":\"/data/CLOUDFRONT_PRIVATE_KEY\",\"value\":\"$(base64 -w0 < cf_private.pem)\"}]"
#   kubectl rollout restart deployment/core-api
#
# 확인은 **길이만** 본다 — 값을 찍으면 개인키가 터미널 스크롤백에 남는다.
#
#   kubectl get secret core-api-secret -o jsonpath='{.data.CLOUDFRONT_PRIVATE_KEY}' | base64 -d | wc -c
#   → 1704        (0 이면 위의 빈 값 함정이다)
#
# 끝나면 서버에 남은 키 파일을 지운다. Secret 에 들어갔으면 홈 디렉터리에 평문으로
# 둘 이유가 없다.
#
#   shred -u cf_private.pem
#
# ── 나중에 필요해질 IAM 권한 ───────────────────────────────────────────────
# 서명 발급 자체는 AWS API 를 부르지 않는다(로컬 서명이라 IAM 이 필요 없다).
# 다만 §8.2 의 `PUBLIC → PRIVATE` 전환을 구현할 때는 무효화 호출이 붙는다 —
# 그때 `motif-core-api` 사용자에 아래를 더한다(ADR-0010 "남은 배선" 9번):
#
#   {"Effect":"Allow","Action":["cloudfront:CreateInvalidation"],
#    "Resource":"arn:aws:cloudfront::<계정ID>:distribution/<배포ID>"}
#
# ── 서명키 길이 (여기서 한 번 크게 데였다) ──────────────────────────────────
# JwtProvider·AdminJwtProvider 는 `secret.getBytes(UTF_8)` 를 그대로 HMAC 키로
# 쓴다. Base64 디코드가 아니다 — **문자 수가 곧 바이트 수**다. HS256 은 256비트
# 이상을 요구하므로 값은 **32자 이상**이어야 한다. 짧으면 기동 중 아래로 죽는다:
#
#   io.jsonwebtoken.security.WeakKeyException:
#     The specified key byte array is 152 bits which is not secure enough ...
#
# 2026-09-13 에 ADMIN_JWT_SECRET 이 19자로 들어가 core-api 가 CrashLoopBackOff
# 났다. `openssl rand -hex 32`(64자)를 쓰면 길이를 고민할 일이 없다.
#
# ── 생성 ────────────────────────────────────────────────────────────────────
# 서버에서 한 줄로 실행한다. 사람이 값을 보거나 입력하지 않는다 — 옮겨오는
# 값은 원본 Secret 에서 클러스터 안으로 바로 건너가고, 서명키는 그 자리에서
# 만들어진다. GOOGLE_CLIENT_ID 만 사람이 채운다.
#
#   kubectl create secret generic core-api-secret \
#     --from-literal=DB_PASSWORD="$(kubectl get secret postgres-secret -o jsonpath='{.data.CORE_APP_PASSWORD}' | base64 -d)" \
#     --from-literal=MQ_PASSWORD="$(kubectl get secret rabbitmq-secret -o jsonpath='{.data.RABBITMQ_CORE_PASSWORD}' | base64 -d)" \
#     --from-literal=REDIS_PASSWORD="$(kubectl get secret redis-secret -o jsonpath='{.data.REDIS_PASSWORD}' | base64 -d)" \
#     --from-literal=JWT_SECRET="$(openssl rand -hex 32)" \
#     --from-literal=ADMIN_JWT_SECRET="$(openssl rand -hex 32)" \
#     --from-literal=GOOGLE_CLIENT_ID='<팀 비밀 저장소 참조>'
#
# 키 하나만 고칠 때는 patch 다. 고친 뒤 재시작해야 파드가 새 값을 읽는다
# (envFrom 은 파드 생성 시점에 해석된다).
#
#   kubectl patch secret core-api-secret -p "{\"stringData\":{\"ADMIN_JWT_SECRET\":\"$(openssl rand -hex 32)\"}}"
#   kubectl rollout restart deployment/core-api
#
# 주의
#   - 원본 비밀번호를 회전해도 이 Secret 은 따라 바뀌지 않는다. 해당 키를
#     patch 하고 `kubectl rollout restart deployment/core-api` 한다.
#   - 검증은 값을 찍지 말고 길이만 본다.
#     `kubectl get secret core-api-secret -o jsonpath='{.data.DB_PASSWORD}' | base64 -d | wc -c`
#   - 서명키를 회전하면 발급돼 있던 토큰이 전부 무효가 된다. 어드민은 재로그인
#     뿐이라(§1.2 refresh 없음) 영향이 작지만, JWT_SECRET 회전은 팬 앱 전원
#     로그아웃이다.
apiVersion: v1
kind: Secret
metadata:
  name: core-api-secret
type: Opaque
stringData:
  DB_PASSWORD: <팀 비밀 저장소 참조: postgres core_app 비밀번호>
  MQ_PASSWORD: <팀 비밀 저장소 참조: rabbitmq core-api 비밀번호>
  REDIS_PASSWORD: <팀 비밀 저장소 참조: redis 비밀번호>
  JWT_SECRET: <openssl rand -hex 32 — 32자 이상>
  ADMIN_JWT_SECRET: <openssl rand -hex 32 — 32자 이상, JWT_SECRET 과 다른 값>
  GOOGLE_CLIENT_ID: <팀 비밀 저장소 참조: 구글 OAuth 클라이언트 ID>
  AWS_ACCESS_KEY_ID: <우리 계정 IAM 사용자 motif-core-api 의 액세스 키 ID>
  AWS_SECRET_ACCESS_KEY: <같은 사용자의 비밀 액세스 키 — 생성 화면에서만 보인다>
  # 여러 줄 PEM 이라 stringData 로 넣지 않는다 — 위 "주입" 의 base64 patch 를 쓴다
  CLOUDFRONT_PRIVATE_KEY: <cf_private.pem 내용 (PKCS#8, BEGIN PRIVATE KEY)>
  MOTIF_WORKER_TOKEN: <openssl rand -hex 32 — 같은 값을 AI 팀 Secret Manager 에도>
