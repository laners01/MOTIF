# 필요한 키 이름만 알리는 예시다. 실제 값은 절대 커밋하지 않는다.
#
# 확장자가 .txt 인 이유: .yaml 이면 `kubectl apply -f infra/k8s/40-core-api/`
# 로 디렉터리를 적용할 때 이 파일까지 적용되어 실제 Secret 을 자리표시자
# 값으로 덮어쓴다. (Postgres 에서 실제로 겪은 사고다.)
#
# 값의 출처 — 새로 만드는 비밀번호가 아니다. 이미 서버에 있는 계정의 것을 그대로 쓴다.
#   DB_PASSWORD : postgres-secret 의 CORE_APP_PASSWORD (계정 core_app)
#   MQ_PASSWORD : rabbitmq-secret 의 RABBITMQ_CORE_PASSWORD (계정 core-api, vhost /motif)
# 두 값 모두 팀 비밀 저장소 참조.
#
# 실제 생성은 서버에서 한 줄로 실행한다. 사람이 값을 보거나 입력하지 않는다
# — 두 원본 Secret 에서 클러스터 안으로 바로 옮긴다.
#
#   kubectl create secret generic core-api-secret --from-literal=DB_PASSWORD="$(kubectl get secret postgres-secret -o jsonpath='{.data.CORE_APP_PASSWORD}' | base64 -d)" --from-literal=MQ_PASSWORD="$(kubectl get secret rabbitmq-secret -o jsonpath='{.data.RABBITMQ_CORE_PASSWORD}' | base64 -d)"
#
# 주의
#   - 원본 비밀번호를 회전해도 이 Secret 은 따라 바뀌지 않는다. delete 후 위
#     명령을 다시 실행하고 `kubectl rollout restart deployment/core-api` 한다.
#   - 검증은 값을 찍지 말고 길이만 비교한다(원본과 같아야 한다).
#     `kubectl get secret core-api-secret -o jsonpath='{.data.DB_PASSWORD}' | base64 -d | wc -c`
#   - 이 두 값은 fallback 이 없다(application-prod.yml). 빠뜨리면 기동 자체가
#     실패한다 — 조용히 기본값으로 뜨는 사고를 막기 위한 의도된 설계다.
#   - Redis 는 아직 여기 없다. app-core-api 에 Redis 설정이 없기 때문이며,
#     랭킹·캐시가 붙는 Phase 1 에 REDIS_PASSWORD 를 추가한다.
apiVersion: v1
kind: Secret
metadata:
  name: core-api-secret
type: Opaque
stringData:
  DB_PASSWORD: <팀 비밀 저장소 참조: postgres core_app 비밀번호>
  MQ_PASSWORD: <팀 비밀 저장소 참조: rabbitmq core-api 비밀번호>
