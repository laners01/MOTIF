# 필요한 키 이름만 알리는 예시다. 실제 값은 절대 커밋하지 않는다.
#
# 확장자가 .txt 인 이유: .yaml 이면 `kubectl apply -f infra/k8s/45-app-media/`
# 로 디렉터리를 적용할 때 이 파일까지 적용되어 실제 Secret 을 자리표시자
# 값으로 덮어쓴다. (Postgres 에서 실제로 겪은 사고다.)
#
# ── 값의 출처 ───────────────────────────────────────────────────────────────
# 옮겨오는 값 (새로 만들지 않는다. 이미 서버에 있는 계정의 것을 쓴다):
#   DB_PASSWORD : postgres-secret 의 CORE_APP_PASSWORD (계정 core_app)
#                 core-api 와 **같은 DB 계정**이다. 워커가 갱신하는
#                 challenges·composite_jobs 가 motif_core 스키마이고 그
#                 소유자가 core_app 이라 나눌 수가 없다.
#   MQ_PASSWORD : rabbitmq-secret 의 RABBITMQ_MEDIA_PASSWORD
#                 (계정 media, vhost /motif — 2026-09-14 신설)
#
# ── AWS 키 ──────────────────────────────────────────────────────────────────
#   AWS_ACCESS_KEY_ID / AWS_SECRET_ACCESS_KEY
#
# **application-prod.yml 이 참조하지 않는다.** AWS SDK 가 환경변수에서 직접
# 읽으므로 빠져도 파드는 정상 기동하고 프로브도 통과한다 — 빠진 것이 첫 잡의
# AccessDenied 로만 드러난다.
#
# 왜 필요한가: 운영 서버는 Lightsail 이고 IMDS 가 `AmazonLightsailInstanceRole`
# 의 임시 자격증명(ASIA…)을 흘린다. 그건 **SSAFY 계정** 것이고 motif-media
# 버킷은 **우리 계정**에 있다 — 크로스 계정이라 서명은 되는데 S3 가 거부한다.
# SDK 자격증명 체인에서 환경변수가 IMDS 보다 앞이라는 점을 이용해 덮어쓴다.
# (backend/CLAUDE.md "S3 자격증명 — IMDS 를 믿지 마라")
#
# ── core-api 키를 재사용하지 않는다 ─────────────────────────────────────────
# 별도 IAM 사용자 `motif-app-media` 로 판다. 키를 공유하면 하나가 털렸을 때
# 둘 다 갈아야 하고, CloudTrail 에서 누가 한 호출인지 구분되지 않는다.
#
# 워커는 core-api 보다 권한이 넓다 — **원본을 읽고 산출물 트리를 쓴다**:
#
#   {"Effect":"Allow","Action":["s3:GetObject","s3:PutObject"],
#    "Resource":"arn:aws:s3:::motif-media/*"},
#   {"Effect":"Allow","Action":["s3:ListBucket"],
#    "Resource":"arn:aws:s3:::motif-media"}
#
#   - ListBucket 의 Resource 에 `/*` 를 붙이면 조용히 무효다(버킷 단위 액션이다)
#
# ── 생성 ────────────────────────────────────────────────────────────────────
# 서버에서 한 줄로 실행한다. 옮겨오는 두 값은 사람 눈을 거치지 않고 클러스터
# 안에서 건너간다. AWS 키만 사람이 콘솔에서 받아 채운다.
#
#   kubectl create secret generic app-media-secret \
#     --from-literal=DB_PASSWORD="$(kubectl get secret postgres-secret -o jsonpath='{.data.CORE_APP_PASSWORD}' | base64 -d)" \
#     --from-literal=MQ_PASSWORD="$(kubectl get secret rabbitmq-secret -o jsonpath='{.data.RABBITMQ_MEDIA_PASSWORD}' | base64 -d)" \
#     --from-literal=AWS_ACCESS_KEY_ID='<IAM 사용자 motif-app-media 의 키 ID>' \
#     --from-literal=AWS_SECRET_ACCESS_KEY='<같은 사용자의 비밀 키 — 생성 화면에서만 보인다>'
#
# 키 하나만 고칠 때는 patch 다. 고친 뒤 재시작해야 파드가 새 값을 읽는다
# (envFrom 은 파드 생성 시점에 한 번만 해석된다).
#
#   kubectl patch secret app-media-secret -p "{\"stringData\":{\"AWS_ACCESS_KEY_ID\":\"...\"}}"
#   kubectl rollout restart deployment/app-media
#
# 확인 — 넣었다고 믿지 말고 본다.
#   kubectl exec deploy/app-media -- printenv AWS_ACCESS_KEY_ID
#   kubectl get secret app-media-secret -o jsonpath='{.data.DB_PASSWORD}' | base64 -d | wc -c
#
# 주의
#   - 원본 비밀번호를 회전해도 이 Secret 은 따라 바뀌지 않는다. 해당 키를
#     patch 하고 rollout restart 한다.
#   - 검증은 값을 찍지 말고 길이만 본다.
apiVersion: v1
kind: Secret
metadata:
  name: app-media-secret
type: Opaque
stringData:
  DB_PASSWORD: <postgres-secret 의 CORE_APP_PASSWORD 와 같은 값>
  MQ_PASSWORD: <rabbitmq-secret 의 RABBITMQ_MEDIA_PASSWORD 와 같은 값>
  AWS_ACCESS_KEY_ID: <우리 계정 IAM 사용자 motif-app-media 의 액세스 키 ID>
  AWS_SECRET_ACCESS_KEY: <같은 사용자의 비밀 액세스 키>
