# app-media — 미디어 후처리

`job.media` 를 소비해 재생용 산출물을 만든다. 결정문은
[ADR-0010](../docs/adr/0010-video-delivery.md).

```
S3 원본(MP4) → 렌디션 2종(720p/480p) → HLS(fMP4) → 썸네일 → S3 → DB 키 기록
```

합성 워커 결과와 어드민이 올린 챌린지 원본이 **같은 경로**로 들어온다.
인코딩 파라미터를 한 곳에서만 관리하기 위한 구조다 — 두 경로에 복사하면
GOP 정렬이 어긋나는 순간 **에러 없이 화질 전환만** 안 된다.

## 배치 — 아직 결정 전

| 후보 | 램 | CPU 경합 | S3 왕복 |
|---|---|---|---|
| SSAFY 노드 (현재) | +0.75GB | **core-api 와 경합** | 잡당 ~60MB |
| GPU 서버 (대여 후) | 0 | 없음 | 합성 결과가 로컬에 있으면 없음 |

**GPU 서버 대여 전까지는 SSAFY 노드에 둔다.** 15GB 단일 노드에 예산이
~9.4GB 잡혀 있으므로(ADR-0009) 피해를 묶어두는 설정이 필요하다.

- `spring.rabbitmq.listener.simple.concurrency: 1` — 한 번에 한 건.
  **큐가 밀리는 편이 API 가 느린 것보다 낫다**
- 매니페스트에 `resources.limits.cpu` 를 건다(1코어 권장). 인코딩이 길어질 뿐
  core-api 는 살아 있다. 실측 0.1배속이 1코어에서 ~0.3배속이 되어 60초 영상에
  18초 남짓이다

대여가 끝나면 **파드만 옮긴다** — 코드·이벤트 계약 변경 없음.

## 지금 돌릴 수 있는 것

GPU 워커가 없어 **합성 경로는 안 돈다**. 어드민이 올리는 **챌린지 원본**
(`CHALLENGE_ORIGIN`)은 GPU 와 무관해 지금 처리 가능하다 — 안드로이드가 HLS
재생을 붙여볼 영상이 여기서 나온다.

## 컨테이너 요구사항

**베이스 이미지에 ffmpeg 가 있어야 한다.** 다른 모듈은 JRE 만 있으면 되지만
여기는 ffmpeg·ffprobe 를 프로세스로 부른다. ADR-0008 레이어드 JAR 방식은
그대로 쓰되 베이스만 달라진다(이미지 ~100MB 증가).

## 안드로이드 확인용 실물

실제 팀 영상(60초 1080p)을 이 파이프라인으로 가공해 CDN 에 올려뒀다.
**Media3 의 fMP4 + `EXT-X-BYTERANGE` 지원 확인**(인계 문서 확인 요청 ①)에 쓰면 된다.

```
https://d21so2cpi8si9r.cloudfront.net/poc/hls/master.m3u8
https://d21so2cpi8si9r.cloudfront.net/poc/hls/thumb.jpg
```

검증한 것 — Range 206(`content-range: bytes 0-1023/7905450`), 마스터·화질별
재생목록 모두 ffmpeg 로 연속 재생, `Content-Type` 정상.

| | |
|---|---|
| 원본 | 25.8MB (1080p, 60초) |
| 산출물 합계 | 12.4MB (48%) |
| 480p / 720p | 4.2MB / 7.5MB |
| 썸네일 | 59.6KB |
| 가공 시간 | 6.7초 |

## 검사

```bash
./gradlew :app-media:test
```

핵심은 `화질_간_키프레임이_정확히_일치한다` 다. 이게 깨지면 예외도 로그도 없이
화질 전환만 안 되므로 사람이 눈으로 보기 전엔 모른다.
