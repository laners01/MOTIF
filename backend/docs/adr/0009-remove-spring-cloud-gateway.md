# ADR-0009. Spring Cloud Gateway를 제거하고 인증을 core-api로 되돌린다

- 상태: 승인
- 일자: 2026-09-09
- 결정자: 백엔드·인프라 (팀 회의)
- 관련: **ADR-0002를 대체함**, ADR-0004(스택 선정 — "각 서버 내 Spring Security
  → SCG 엣지 인증" 행을 **부분 대체**), 아키텍처 설계서 v0.2 → v0.3,
  아키텍처 구성도 v0.7, `backend/settings.gradle`,
  `infra/k8s/90-ingress/`(Traefik 미들웨어)

## 컨텍스트

ADR-0002는 Traefik(엣지: TLS·라우팅) 뒤에 SCG(애플리케이션 게이트웨이:
인증·인가·유저당 리밋)를 두는 2층 구성을 확정했다. "Traefik은 어디로, SCG는
누가를 푼다"는 분리였고, 근거의 상당 부분은 **업스트림이 늘어날 것**이라는
전제 위에 있었다.

그 뒤 확정된 조건들이 전제를 바꿨다.

- **HTTP를 받는 앱이 하나뿐이다.** 알림 서비스는 이벤트 소비 전용으로
  확정됐고(HTTP 엔드포인트 없음 — 관리 포트만), 어드민은 별도 실행체가 아니라
  core-api 안의 `/admin`이다. 라우팅 대상이 1개다.
- **램이 가장 희소한 자원이다.** 실행 환경은 15GB 단일 노드다. 총 예산이
  ~9.4GB로 잡혀 있고, 어드민 파드 분리 같은 이후 선택지는 남은 여유에서
  나온다.

즉 SCG의 실질 업무는 "JWT 필터 하나를 통과시키는 것"으로 줄었고, 그 대가는
JVM 파드 하나다.

## 결정

**D1. SCG를 제거한다.** `app-gateway` 모듈과 `settings.gradle` include를
삭제한다. 버전 카탈로그의 `spring-cloud` 트레인 핀은 지우지 않고 주석으로
보류한다(재도입 시 그 줄만 되살린다).

**D2. 인증·인가는 core-api의 Spring Security 필터 체인이 수행한다.**
JWT 검증, 어드민 JWT의 **서명키 분리**가 여기에 들어간다. 구현 시점은
Phase 1(인증)로 ADR-0002와 동일하다 — 위치만 게이트웨이에서 앱으로 옮긴다.

**D3. `/admin`의 팀 IP·테일넷 제한은 Traefik 미들웨어(`ipAllowList`)가 맡는다.**
네트워크 수준 제한은 원래 엣지의 일이고, 앱에 두면 프록시 뒤 클라이언트 IP를
헤더로 신뢰해야 한다. 인그레스는 `/api`와 `/admin`을 나눠 후자에만 미들웨어를
붙인다.

**D4. 유저당 레이트리밋도 core-api 안으로 옮긴다.** ADR-0002 근거 3(합성 요청이
GPU를 수십 초 점유하므로 사용자 단위 상한이 필요하고, Traefik의 IP 기준 리밋은
NAT 뒤 사용자를 구분하지 못한다)은 **그대로 유효하다**. SCG를 지운다고 리밋이
필요 없어지는 것이 아니므로, 기존 Redis를 쓰는 token bucket을 앱 필터로
구현한다(Phase 1, 인증 필터와 같은 체인).

**D5. 요청 경로는 Traefik → core-api 직결이다.** SCG가 채우던 내부 헤더 계약
(`X-User-Seq`, `X-User-Role`)은 사라진다. 앱이 토큰을 직접 검증하므로 헤더를
신뢰할 필요가 없고, 아무도 읽지 않으므로 스푸핑 표면도 함께 사라진다.

## 근거

1. **역할 중복.** 라우팅 대상이 1개인 동안 SCG가 실제로 하는 일은 JWT 필터
   통과뿐이다. 같은 로직을 Spring Security로 옮기는 데 추가 비용이 없다 —
   어차피 Phase 1에 쓸 코드다.
2. **램 회수.** JVM 파드 1개(~0.75GB limit)를 제거한다. 총 예산 ~9.4GB →
   ~8.6GB. 어드민 파드 분리(+0.75GB) 여지를 미리 확보한다.
3. **홉 감소.** 요청 경로에서 네트워크 홉 1개가 빠진다 — 지연과 장애 지점이
   함께 줄고, 배포체도 하나 줄어 파이프라인 복제 대상이 아니게 된다.
4. **단일 장애점 하나가 사라진다.** ADR-0002는 SCG의 SPOF를 Phase 4에서
   replica 2로 푼다고 유보했다. 그 램 0.75GB도 함께 회수된다.

## 검토한 대안

| 대안 | 기각 사유 |
|---|---|
| SCG 유지(ADR-0002 현행) | 라우팅 대상 1개에 JVM 파드 하나. 15GB 단일 노드에서 그 0.75GB는 더 급한 곳이 있다 |
| SCG를 유지하되 램만 조인다 | JVM 하한이 있어 유의미하게 줄지 않는다. 파드를 남기는 값이 필터 하나뿐이다 |
| SCG를 리밋·어드민 분기 전용으로 축소 | 남기는 이유가 "있으니까"가 된다. 두 기능 모두 앱 필터·엣지 미들웨어로 옮길 수 있다 |
| Traefik ForwardAuth | ADR-0002에서 이미 기각 — 검증용 서비스를 세워야 해 비용이 SCG와 같고 로직이 인프라 설정으로 이원화된다 |

## 결과와 트레이드오프

- **재작업이 예약된다.** 어드민 파드를 분리하는 시점에 공통 인증 지점이 다시
  필요해지고, core-api의 인증 로직 일부를 게이트웨이로 올리는 작업이 생긴다.
  이것이 이 결정의 실질 비용이다. 대신 그 시점까지 램 0.75GB를 쓴다.
- **발표에서 게이트웨이 계층이 있는 구성도의 완성도를 포기한다.**
  → "HTTP 서비스가 2개 이상일 때 게이트웨이를 도입한다"는 원칙으로 방어한다.
  없어서 못 그린 것과 조건을 정해두고 안 넣은 것은 다르다.
- 인증 코드가 앱 안에 있으므로, HTTP 서비스가 늘면 중복이 생긴다 — 아래
  트리거가 그 지점을 미리 못박는다.

## 재도입 트리거

**HTTP 서비스가 2개 이상이 되는 시점.** 구체적으로 어드민을 별도 실행 모듈
(`app-admin`)로 분리해 테일넷 전용 파드로 배포할 때다. 그 시점에 공통 인증과
라우팅 분기를 게이트웨이로 승격하고, 이 ADR을 새 ADR로 대체한다.
(ADR-0007의 `registry:2`와 같은 형태의 보류다 — 폐기가 아니라 조건부 연기.)

## 부록 — 발표 Q&A

**Q. 게이트웨이 없이 인증을 앱에 두면 서비스가 늘 때마다 인증이 중복되지
않나?**

맞다. 그래서 HTTP 서비스가 2개가 되는 시점(어드민 분리)을 게이트웨이 재도입
트리거로 정의해뒀다. 지금은 라우팅 대상이 1개라, 게이트웨이가 JVM 750MB를
쓰며 필터 하나를 돌리는 구성이었다. 15GB 단일 노드에서 그 램은 더 급한 곳이
있다.
