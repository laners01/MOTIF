# ADR-0002. 엣지(Traefik)와 애플리케이션 게이트웨이(SCG)의 2층 구성

- 상태: **대체됨** — ADR-0009(2026-09-09, SCG 제거)
- 일자: 2026-09-02
- 관련: 아키텍처 설계서 §2, MODERA 회고(Nginx 단일 프록시)

## 컨텍스트

클러스터 입구에는 이미 Traefik이 있다(TLS 종단, 인증서 자동 갱신, 경로
라우팅). 여기에 Spring Cloud Gateway를 별도 실행체로 두는 것이 과잉인지
질문이 나왔다. 직전 프로젝트 MODERA는 Nginx 단일 프록시 뒤에서 각 서버가
직접 JWT를 검증했다.

## 결정

Traefik과 SCG를 **서로 다른 층**으로 함께 둔다.

| | Traefik (엣지) | SCG (애플리케이션 게이트웨이) |
|---|---|---|
| 아는 것 | TLS, 도메인, 경로 | JWT 클레임, 사용자, 역할 — 도메인 개념 |
| 책임 | 암호화 종단, 인증서, L7 라우팅 | 인증·인가, 유저당 레이트리밋, 내부 헤더 계약 |

한 줄 요약: **Traefik은 "어디로"를 풀고, SCG는 "누가"를 푼다.**

## 근거

1. **인증의 단일 지점과 내부 헤더 계약.** SCG가 JWT를 한 번 검증하고 뒤로는
   `X-User-Seq`, `X-User-Role`만 전달한다. 백엔드 서비스에서 토큰 파싱이
   사라진다. 외부에서 들어온 `X-User-*` 헤더는 SCG가 무조건 제거하고 자기가
   채운다(스푸핑 차단).
2. **정책이 다른 두 영역의 분기점.** `/api`(사용자 JWT)와 `/admin`(서명키가
   분리된 어드민 JWT + IP 제한)의 갈림을 게이트웨이 라우트 한 곳에서 감사할
   수 있다.
3. **유저당 레이트리밋.** Traefik의 리밋은 IP 기준이라 NAT 뒤 사용자를
   구분하지 못한다. 합성 요청은 GPU 수십 초를 점유하는 비싼 자원이므로
   사용자 단위 상한이 필요하다. SCG `RequestRateLimiter`(token bucket)가
   기존 Redis를 재사용한다.
4. **업스트림 증가 대비.** 합성 상태 SSE가 알림 서비스의 HTTP 엔드포인트로
   추가되면(ADR 백로그) 업스트림이 둘이 된다. 라우팅 변경이 게이트웨이 설정
   한 줄로 끝난다.

## 검토한 대안

- **SCG 없이 각 서비스가 Spring Security로 검증(MODERA 방식)** — 서비스가
  하나일 때는 충분하다. 그러나 어드민/사용자 정책 분리와 유저당 리밋을
  서비스 안에 흩뿌리게 되고, 업스트림이 늘 때마다 중복이 커진다.
- **Traefik ForwardAuth 플러그인** — 결국 검증용 별도 서비스를 세워야 해서
  SCG와 비용이 같고, 로직이 인프라 설정에 박혀 Spring 코드와 이원화된다.

## 결과와 트레이드오프

- 홉 +1 (수 ms), 배포체 +1.
- SCG가 단일 장애점이 된다 → Phase 4 하드닝에서 replica 2로 올린다.
- 스캐폴드에는 모듈과 최소 라우트만 만들고, JWT 필터·레이트리밋은 Phase 1
  (인증)과 함께 구현한다. Phase 0 DoD는 Traefik → core-api 직결로 충족한다.

## 부록 — 로드 밸런싱과 무상태

별도 LB는 도입하지 않는다. k8s Service가 L4 분배를 담당하며(`replicas: 2`가
곧 분배 시작), 우리 몫은 "파드가 몇 개여도 같은 응답"을 보장하는 것이다:
세션 없음(JWT), 카운터·캐시는 Redis, 파일은 S3, 배치 중복은 ShedLock.
core-api는 Phase 0에서 1로 시작해 Phase 1에서 2로 올리고, 그 시점에
ShedLock이 실제로 중복 실행을 막는지 검증한다. SSE 도입 시 이벤트가 연결을
가진 파드에 도달하도록 Redis pub/sub 릴레이를 전제한다(알림 서비스 스케일
시점의 조건).
