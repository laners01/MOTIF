# ADR-0011. Redis 를 단명 상태 저장소로 쓴다 — presign 발급 기록부터

- 상태: 승인
- 일자: 2026-09-16
- 관련: API 명세 §4.3·§4.4, ADR-0004(스택 선택), `S15P21D104-280`

## 컨텍스트

`spring-boot-starter-data-redis` 는 처음부터 `app-core-api` 의 의존성에 있고
`local`·`local-remote`·`prod` 세 프로파일 모두 접속 정보를 갖고 있다. 그런데
**이 커밋 이전까지 그것을 쓰는 코드가 한 줄도 없었다.** 인증(refresh token)은
`refresh_tokens` 테이블로, 잡 상태는 `composite_jobs` 로 전부 DB 에 들어갔다.

§4.4 프로필 이미지 반영이 처음으로 "DB 에 넣기 애매한 상태"를 요구한다. 명세는
403 `FORBIDDEN` 조건을 *"본인 발급 키가 아님(프리픽스·발급 기록 불일치)"* 이라고
적었는데, **프리픽스만으로는 막히지 않는다** — 남의 `profileImageUrl` 은 §4.6 이
공개하므로 그 키를 그대로 §4.4 에 보내면 통과한다. 발급 기록이 필요하다.

그 기록의 성질이 특이하다:

- **수명이 정확히 300초다.** presign URL 이 만료되면 그 키를 주장할 근거도 함께
  사라지는 것이 맞다 — 둘은 같은 사건의 양면이다.
- 사용자당 여러 개가 동시에 살아 있을 수 있다(앱이 presign 을 재시도하는 흐름).
- 소비되면 즉시 버린다. 이력으로서 가치가 없다.

## 결정

**단명 상태는 Redis 에 둔다. 영속 상태는 계속 PostgreSQL 이다.**

경계는 "만료가 데이터의 본질인가"로 가른다. TTL 이 비즈니스 규칙 자체이고 남겨야
할 이력이 아니면 Redis, 그 밖은 DB 다.

첫 적용이 `ProfileImagePresignRegistry` 다 — 키 `profile-image:presign:{userSeq}:{imageKey}`,
TTL 은 presign 만료와 같은 값을 **설정 한 곳에서** 가져온다.

### 왜 DB 컬럼이 아닌가

`users.pending_profile_image_key` 같은 칸을 두면 Liquibase changeSet 과 DB 명세
갱신이 따라붙는데, **거의 항상 NULL 인 칸 하나를 위해서다.** 게다가 만료를 DB 가
표현하지 못하므로 발급 시각 칸을 하나 더 두고 비교하거나 정리 배치를 짜야 한다 —
Redis 가 TTL 로 공짜로 주는 것을 손으로 구현하는 셈이다. 동시 발급 여러 개를
담으려면 칸이 아니라 테이블이 되고, 그러면 "300초 뒤 지우는 테이블"이 생긴다.

### 왜 서명에 넣지 않는가

`imageKey` 자체에 소유자를 HMAC 으로 새기는 방법도 있다(상태가 아예 없어진다).
버린 이유는 키가 **S3 오브젝트 경로이면서 동시에 토큰**이 되기 때문이다 — 경로
규약(`MediaKeys`)과 인증 규약이 한 문자열에 얽히고, 키 회전이 곧 기존 오브젝트
경로 무효화가 된다.

### 왜 경로에 `userSeq` 를 넣지 않는가

`profiles/{userSeq}/{uuid}.jpg` 로 하면 상태 없이 소유자를 판정할 수 있다. 버린
이유는 둘이다. ① `AdminMediaKind.ARTIST_PROFILE` 이 `profiles/{uuid}.jpg` 를 쓰며
*"사용자 프로필과 프리픽스를 공유한다"* 고 선언해 뒀는데 모양이 갈린다.
② 공개 CDN 네임스페이스에 순차 정수가 드러난다(`MediaKeys` 가 피하는 것과 같은
이유).

## 결과

**얻는 것**

- 만료 처리를 짜지 않는다. TTL 이 곧 규칙이다.
- 스키마가 늘지 않는다. 이 성질의 상태가 앞으로 더 생겨도(멱등 키 dedup —
  ADR-0005 가 이미 선택지로 적어 둔 것, 레이트 리밋, 단기 캐시) 둘 자리가 있다.

**잃는 것 · 감수하는 것**

- **Redis 가 죽으면 프로필 이미지 변경이 막힌다.** 다만 §4.3 도 같이 막히므로
  "발급은 됐는데 반영만 안 되는" 어정쩡한 상태는 생기지 않는다(fail-closed).
  그 이상의 가용성이 필요한 기능에는 이 패턴을 쓰지 않는다.
- **Redis 를 잃으면 진행 중이던 발급 기록이 사라진다.** 사용자는 업로드를 다시
  한다. 재현 가능한 300초짜리 상태라 감수한다 — 이 경계를 넘는 데이터, 즉 잃으면
  사용자가 복구할 수 없는 것은 Redis 에 두지 않는다.
- 로컬 개발에 Redis 가 필요해진다. `backend/local-infra` compose 에 이미 있어
  새 요구는 아니다.

## 대안

| 안 | 버린 이유 |
|---|---|
| DB 컬럼 | 거의 NULL 인 칸 + 만료 처리를 손으로 구현 + 동시 발급을 못 담는다 |
| 키에 HMAC | S3 경로와 인증 토큰이 한 문자열에 얽힌다 |
| 경로에 `userSeq` | 어드민 프로필 키 규약과 갈리고, CDN 에 순차 정수가 드러난다 |
| 발급 기록 없이 프리픽스만 | 명세의 403 분기를 못 지킨다. 남의 공개 키로 통과한다 |
