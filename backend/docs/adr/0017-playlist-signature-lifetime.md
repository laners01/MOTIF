# ADR-0017. 재생목록 서명 수명을 목록 수명에 맞추고, 만료를 셋으로 가른다

- 상태: 채택
- 날짜: 2026-09-23
- 대체: [ADR-0012](0012-signed-prefix-playback.md) 의 **만료 전제**(10분 + 403 사후 재발급).
  결정 자체는 유지 — "프리픽스 서명 + 클라이언트 부착" 은 그대로다.
- 관련: [ADR-0013](0013-signed-only-media.md), [ADR-0015](0015-redis-view-aggregation.md),
  API 명세 §1.7 · §6.1 · §8.9

## 맥락

§6.1 HOT 목록의 `videoUrl` 이 일정 시간 뒤 403 이 된다는 보고가 있었다. 썸네일은 6시간
서명이라 **목록은 멀쩡해 보이고 재생만 안 된다.**

값 자체는 명세대로다. `motif.media.signing.ttl` 은 10분이고 §1.7 "만료 기본 10분" ·
ADR-0012 R4 와 일치한다. 어긋난 것은 **그 10분이 성립하는 전제**다.

ADR-0012 는 만료를 사후에 복구한다 — 조각이 403 이면 인터셉터가
`POST /api/v1/media/{jobUuid}/signature` 를 부르고 재시도한다. 이 전제가 성립하려면 403 이
**드물고**, 한 번의 스톨이 **한 번**이어야 한다. 홈 HOT 에 자동재생을 넣기로 하면서 둘 다
깨졌다.

- **서명 범위가 영상 하나다**(ADR-0012 — 상위 경로로 넓히면 파라미터가 새는 순간 그 범위가
  통째로 열린다). 그래서 재발급도 영상당 1회다. 10개짜리 페이지를 자동재생으로 훑으면
  갱신 왕복이 10번이고, 그때마다 카드가 멈춘다.
- **목록의 수명이 서명보다 길다.** §1.6 은 홈 3섹션에 TTL 5분 + stale-while-revalidate 를
  주고("탭 복귀 시 TTL 내 요청 0회, 경과 시 기존 화면 유지 + 조용한 갱신"), §6.1 R4 는
  캐러셀이 받은 목록을 뷰어에 그대로 넘기며 **재조회하지 않는다**고 못박았다. 커서 시퀀스는
  스냅샷 버전 키가 사는 동안(`motif.view.video-ranking.retain` = 2시간) 유효하다.

즉 서버가 "10분짜리 URL" 을 내주면서 클라이언트에게는 "2시간 동안 이 목록을 그대로 쓰라"고
말하고 있었다.

## 결정

**재생목록 서명의 만료를 목록이 살아 있는 최대 구간에 맞추고, 하나였던 `ttl` 을 복구 경로
유무에 따라 셋으로 가른다.**

```
motif.media.signing.playlist-ttl    2h     HLS 프리픽스 서명 (재생목록·조각)
motif.media.signing.video-file-ttl  10m    단일 영상 파일 — §7.6 편집본
motif.media.signing.image-ttl       6h     썸네일·프로필
```

**가르는 기준은 대상의 종류가 아니라 복구 경로의 유무다.**

| | 만료되면 | 값 |
|---|---|---|
| 재생목록 | 자동재생 중 스톨. 재발급이 영상당 1회라 사후 복구가 비싸다 | 목록 수명 = 2h |
| 단일 영상 파일 | 앱이 §7.6 을 다시 부르면 새 URL 이다 — 실제로 있는 경로다 | 10m |
| 이미지 | `<img>` 가 깨진 채로 남는다. 다시 받을 계기가 없다 | 6h |

**2시간은 `video-ranking.retain` 과 같은 값이고 우연이 아니다.** 그 시점에 커서 시퀀스가
죽어 목록 자체가 빈 배열이 되므로, 그보다 긴 서명은 재생할 대상이 없고 짧은 서명은 살아
있는 목록을 깨뜨린다. **둘은 같은 것을 재므로 한쪽만 바꾸면 다시 어긋난다.**

`ttl` 이라는 이름을 없앤다. 한 값이 프리픽스 서명과 단일 파일 서명을 함께 덮고 있었고
javadoc 은 "재생목록·조각" 이라고만 적혀 있어, 편집본이 같은 값에 묶여 있다는 사실이
코드에서 읽히지 않았다.

### 돌려주는 만료는 서명에 박힌 값이다

`prefixSignatureExpiry()` 가 서명과 **따로** `Instant.now()` 를 불렀다. 돌려준 시각이 실제
만료보다 뒤라, 그 값에 맞춰 미리 갱신하는 클라이언트가 한 발 늦게 갱신한다. 서명과 만료를
한 번에 만들어 함께 돌려주는 `signPrefixWithExpiry` 로 바꾼다 — 프리페치 갱신이 1차 방어가
되려면 이 값이 정확해야 한다.

## 결과

**얻는 것**

- 자동재생이 성립한다. 목록이 살아 있는 동안 그 목록의 URL 도 살아 있다.
- 만료 셋이 각자의 근거를 갖는다. 어느 하나를 바꿀 때 나머지가 딸려 오지 않는다.
- §7.6 `expiresIn` 이 `resolveVideoFile` 이 실제로 쓰는 만료와 같은 값이 된다.

**잃는 것 · 감수하는 것**

- **권한 회수 지연이 10분 → 2시간이다.** §8.9 `PUBLIC → PRIVATE` · §8.10 삭제 · 정지 ·
  환불이 전부 이 값을 최대 지연으로 갖는다. **목록·조회에서 사라지는 것은 즉시 그대로**고,
  늘어난 것은 **이미 URL 을 받아 간 쪽의 재생 창**뿐이다. 서명에는 무효화 수단이 없으므로
  이것이 상한 그대로다.
- **서명 문자열 위임의 창도 같이 늘었다.** `PRIVATE` 영상의 `videoUrl` 을 통째로 복사해
  넘기면 그동안 재생된다(08-video §8.9 가 이미 적어 둔 성질이다).
- ADR-0012 R4 가 "최대 10분간 그 영상 하나" 로 계산한 손실이 2시간이 된다. 그 문장은 결정
  기록이라 고치지 않고 이 ADR 이 대체한다.

## 대안

| 안 | 버린 이유 |
|---|---|
| 10분 유지 + 응답에 `jobUuid` 를 실어 앱이 프리페치 갱신 | 권한 정밀도를 지키는 제대로 된 답이지만 응답 계약·명세·안드로이드를 함께 건드리고, 갱신이 카드당 1회라 호출 수가 목록 길이에 비례한다. 이 ADR 이 그 길을 막지는 않는다 — `expiresDttm` 을 정확히 만든 것이 그 준비다 |
| 서명 범위를 상위 경로로 넓혀 한 번에 갱신 | 파라미터가 새는 순간 그 범위가 통째로 열린다. ADR-0012 가 명시적으로 거부한 것이다 |
| 6시간(`image-ttl`)에 맞춰 통일 | 재생할 목록이 없는 구간까지 서명이 산다. 회수 지연만 길어지고 얻는 것이 없다 |
| 목록 쪽을 줄인다 — 커서 보존을 10분으로 | `rankDelta` 대비 대상이 3틱 전(1시간) 버전이라 보존이 그보다 짧으면 순위 변동이 **예외도 로그도 없이** 전원 `null` 이 된다(ADR-0015) |
| §6.1 재호출로 페이지 전량을 갱신 | 호출 1회로 URL 을 전부 새로 받는 점은 낫지만, R4 의 "뷰어는 재조회하지 않는다" 를 뒤집어야 하고 스냅샷 버전이 바뀌면 순서까지 흔들린다 |
