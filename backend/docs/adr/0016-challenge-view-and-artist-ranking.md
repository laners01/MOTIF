# ADR-0016. 챌린지 조회수도 같은 버퍼로 모으고, 아티스트 랭킹을 그 위에 다시 세운다

- 상태: 승인
- 일자: 2026-09-21
- 관련: API 명세 §5.1·§7.4, ADR-0015(조회수 Redis 집계), ADR-0009(1 레플리카)

## 컨텍스트

ADR-0015 가 참여 영상(§8.5)의 조회수를 Redis 로 모으고 §6.1 랭킹을 그 위에 다시 세웠다.
**챌린지(§7.4)는 손대지 않고 남겨 뒀다.** 그 결과가 지금 이렇다.

- `challenges.view_count` 는 **여전히 한 번도 증가한 적이 없다.** 올리는 코드가 없다.
- §5.1 아티스트 랭킹은 `(view_count × Wv + participant_count × Wp) × 0.5^(age/H)` 인데,
  조회수 항이 통째로 0 이라 **사실상 참여 수만으로 굴러간다.** 참여 역시 게시 API 가
  붙기 전에는 0 이었으므로 §5.1 상세 문서는 *"전 아티스트 0점 동점"* 이라고 적어 뒀다.

그리고 §5.1 스냅샷을 읽는 곳이 **둘**이다.

| 화면 | 성격 |
|---|---|
| §6.2 홈 Who's On TOP4 | 실시간성이 어울린다 |
| **§3.1 온보딩 인기 아티스트** | 앱을 처음 켠 사람에게 "인기" 를 제시하는 자리다 |

두 번째가 §6.1 HOT 영상과 결정적으로 다르다. **온보딩에서 무명 아티스트가 1위로 뜨면
곤란하다** — 아무도 모르는 이름을 인기라고 내미는 셈이고 구독 전환에 직결된다.

## 결정

### 1. §7.4 를 §8.5 와 같은 구조로 바꾸고, 버퍼를 대상 종류로 일반화한다

경로가 `POST /challenges/view` 가 되고 본문은 `{ "views": { "11": 3 } }` 다. 404 는
없어진다(§8.5 와 같은 근거 — 조회마다 DB 를 확인하면 집계를 Redis 로 뺀 의미가 없다).

버퍼를 복제하지 않는다. `RENAMENX` rotate · 멱등 마커 · 재처리 인덱스가 두 벌이 되면
**한쪽만 고쳐졌을 때 조용히 갈린다.** 대상 종류(`video`/`challenge`)를 받는 한 클래스를
두 빈으로 띄운다.

```
view:{target}:pending              HASH
view:{target}:processing:{ts}      HASH
view:{target}:processing:index     LIST
view:{target}:bucket:{ts}          HASH   TTL
view:{target}:bucket:index         LIST
view:{target}:flush:{ts}           STRING 멱등 마커
```

### 2. 멱등 마커에 대상을 넣는다 — 안 넣으면 한쪽이 조용히 건너뛴다

ADR-0015 의 마커는 `view:flush:applied:{ts}` 로 **대상이 없었다.** 두 대상이 같은 틱에
같은 `{ts}` 로 돌면 먼저 선점한 쪽만 DB 에 반영되고 **나머지 하나는 "이미 반영됨" 으로
보고 건너뛴다** — 예외도 로그도 없이 챌린지 조회수가 통째로 사라진다. 대상을 키에 넣어
닫는다.

**배포 시 주의**: 마커 키 이름이 바뀌므로 배포 순간에 미완료 구간이 남아 있으면 그
구간만 DB 에 두 번 반영될 수 있다. 배포 전에 `view:video:processing:index` 가 비어
있는지 보면 된다(정상 운영에서는 항상 비어 있다).

### 3. §5.1 점수식을 §6.1 과 같은 3항 구조로 바꾼다

```
reaction_total  = Σ_c ( view_count_c + Wp × participant_count_c )
reaction_recent = Σ_c ( 최근 구간 조회수_c )
reaction_prev   = Σ_c ( 그 이전 구간 조회수_c )

tScore = log10(1 + reaction_total)  / log10(1 + T0)
rScore = log10(1 + reaction_recent) / log10(1 + R0)
dRel   = (reaction_recent − reaction_prev) / (reaction_prev + K)
dScore = 0.5 + 0.5 × clamp(dRel / D0, −1, +1)

score  = Wt·tScore + Wr·rScore + Wd·dScore
```

**시간 감쇠를 걷어낸다.** ADR-0015 와 같은 근거다 — 감쇠의 기준이 챌린지 등록 시각이라
오래된 챌린지는 지금 아무리 돌아도 올라올 수 없었다. 버킷이 "지금 얼마나 보고 있는가" 를
직접 준다.

**다만 성격이 바뀐다.** 지금 감쇠는 **챌린지 하나하나**에 걸려 "옛 챌린지 vs 새 챌린지" 를
갈랐다. 새 구조는 아티스트 단위로 합산한 뒤 최근·증감을 보므로 **"이 아티스트가 지금
뜨는가" 만 남는다.** 아티스트 랭킹의 목적에는 이쪽이 맞다고 본다.

### 4. 참여 영상 수는 **누적 항에만** 넣는다

`Wp = 100`("참여 1건 = 조회 100회")은 **누적끼리** 비교하려고 정한 값이다. 1시간 창에서는
참여가 정수 0~2 건이라 환산비가 아니라 **on/off 스위치**가 된다.

| | 1시간 조회 | 1시간 참여 | `Wp=100` 반영 |
|---|---|---|---|
| 아티스트 X | 50 | 0 | 50 |
| 아티스트 Y | 20 | 1 | **120** |

조회가 2.5배 적은 Y 가 이긴다. 우리 규모에서 1시간 참여는 0 아니면 1 이므로 순위가
사실상 "최근 한 시간에 누가 영상을 올렸나" 로 결정된다 — 동전 던지기다. 게다가
`rScore` 가 100 단위로 계단식으로 움직여 `rankDelta` 까지 튄다.

표본이 작을 때 비율을 믿지 않는다는 점에서 `K`(아래)와 같은 계열의 판단이다.

**부수 효과로 설계가 하나 줄었다.** 참여의 시간 창이 필요 없어져
`participation_videos.reg_dttm` 을 읽는 집계 쿼리를 만들지 않는다.

### 5. 가중치는 §6.1 과 다르게 간다

| | 누적 | 최근 | 증감 | 근거 |
|---|---|---|---|---|
| §6.1 영상 HOT | 0.3 | 0.5 | 0.2 | 발견 중심. 휘발성이 장점이다 |
| **§5.1 아티스트** | **0.5** | **0.35** | **0.15** | 온보딩 겸용. 누적 인지도가 필요하다 |

§6.1 값을 그대로 쓰면 검산에서 **신인이 대형 아티스트를 앞선다**(0.827 vs 0.735).
0.5/0.35/0.15 로 두면 "지금 뜨는" 아티스트가 1위인 것은 유지되면서 대형이 신인 위로
돌아온다.

### 6. 스냅샷을 §6.1 과 같은 버전 구조로 통일하고 `prev-interval` 을 폐기한다

지금 `rankDelta` 는 `rank:artist:prev` 를 **별도 주기(10분)** 로 굴려 얻는다. 집계가 20분
단일 배치로 합쳐지면 그 별도 주기를 둘 자리가 없다. 틱을 세는 방식은 재시작에 취약해
쓰지 않는다.

```
rank:artist:current           STRING  버전 포인터
rank:artist:{version}         ZSET    score = rank(1-base)
rank:artist:{version}:delta   HASH    artistSeq → rankDelta
rank:artist:versions          LIST    버전 이력
```

§6.1 과 같은 모양이 되고 대비 구간이 "3틱 전(1시간)" 하나로 통일된다. **정렬을 적재
시점에 확정**하므로 조회가 매번 전량을 꺼내 Java 에서 정렬하던 것도 사라진다.

### 7. §6.1 을 그대로 복사하면 안 되는 것

- **모집단을 좁히지 않는다.** §6.1 은 `view_count > 0` 으로 후보를 줄였다. §5.1 에
  같은 것을 하면 **온보딩 인기 목록에서 신인이 통째로 사라진다.** 비삭제 아티스트는
  챌린지가 0개여도 0점으로 넣는다.
- **`keep` 상한을 두지 않는다.** §5.1 은 필터링과 `totalElements` 때문에 전량이
  필요하다(offset 페이지). 자르면 페이지 수가 틀어진다.
- **동점이 대량으로 발생한다.** 조회·참여가 모두 0인 아티스트가 많다.
  `score DESC → artistSeq ASC` 확정을 유지한다.

### 8. 클라이언트 캐시 TTL 5분은 그대로 둔다 — 배치 주기와의 연결만 끊는다

§1.6 이 *"TTL 5분(랭킹 배치 주기와 동일)"* 이라고 묶어 놨는데 배치가 20분이 된다. TTL 도
20분으로 올리면 **최대 지연이 배치 20분 + 캐시 20분 = 40분**이 된다. 5분을 유지하면
지연 상한이 배치 주기 하나로 묶이고 클라이언트가 그 안에서 빨리 따라잡는다. 같은 데이터를
네 번 확인하게 되지만 응답이 작고 stale-while-revalidate 라 체감 비용이 없다.

## 결과

**얻는 것**

- `challenges.view_count` 가 처음으로 실제 값을 갖는다. §5.1 이 0점 동점에서 벗어난다.
- 조회수 파이프라인이 한 벌이다. rotate·멱등·재처리 로직이 한 곳에만 있다.
- 두 랭킹의 공식·설정·테스트가 같은 모양이 되어 한 머리로 볼 수 있다.

**잃는 것 · 감수하는 것**

- **`T0`·`R0`·`K`·`D0` 네 값이 전부 추정이다.** 실트래픽이 없어 자릿수만 맞췄다. 배치가
  상위 10건의 항별 점수를 로그에 남기므로 하루치를 보고 설정만 고치면 된다.
- **아티스트 랭킹이 §6.1 보다 둔하게 움직인다.** 의도한 것이지만, 시연에서 순위가 잘
  안 바뀌면 `Wt` 를 먼저 의심한다.
- **`prev-interval` 설정이 사라진다.** 시연에서 대비 구간을 줄이려면
  `rank-delta-buckets` 를 내린다.
- §7.4 도 §8.5 와 같은 한계를 물려받는다 — 1회 인정 기준이 미결이라 클라이언트가 보낸
  `count` 를 믿는다(원본 §16 #3).

## 대안

| 안 | 버린 이유 |
|---|---|
| 챌린지용 버퍼를 따로 작성 | rotate·멱등 로직이 두 벌이 된다. 한쪽만 고쳐지는 종류의 버그다 |
| 마커 키를 그대로 두기 | 두 대상이 같은 틱에 돌면 한쪽 DB 반영이 조용히 건너뛰어진다 |
| 참여를 최근·증감 항에도 넣기 | 1시간 창에서 참여가 0~2 라 순위가 동전 던지기가 된다 |
| 참여를 네 번째 독립 항으로 | 참여는 조회보다 2~3 자릿수 드물어 `log` 뒤 거의 상수가 된다. 가중치만 하나 늘어난다 |
| §6.1 과 같은 가중치 | 온보딩 인기 목록에서 무명이 1위로 올라온다 |
| 시간 감쇠 유지 | 오래된 챌린지가 지금 돌아도 올라오지 못한다 |
| `:prev` 를 20분 배치 안에서 틱 세어 갱신 | 재시작하면 카운터가 사라져 대비 구간이 조용히 어긋난다 |
| 클라 TTL 도 20분으로 | 최대 지연이 40분이 된다 |
