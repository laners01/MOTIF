# ADR-0014. 아티스트 검색을 별칭 테이블로 옮긴다 — 다국어 검색

- 상태: 채택
- 날짜: 2026-09-20
- 관계: **API 명세 §5.2 를 재정의하고 §5.9 를 삭제한다**(v0.13) · DB 명세 §41·§42
  신설(v0.17) · 어드민 명세 §3.4.5~8·§3.5.6~9 신설(v0.6)

## 맥락

검색을 다국어로 지원하려 한다. "Karina" 로 치든 "카리나" 로 치든 같은 아티스트가
나와야 하고, "aespa" 를 치면 그 그룹 멤버가 나와야 한다.

지금 구조로는 안 된다. 검색 대상이 `users.nickname` 과 `artist_groups.group_name`
두 칼럼인데, 둘 다 **표시용 단일 값**이다. 이름 칸 하나에 언어를 여러 개 담을 수 없고,
담으려고 칼럼을 늘리면 언어가 추가될 때마다 스키마가 바뀐다.

그리고 §5.2 검색·§5.9 자동완성은 **명세에만 있고 구현이 없다**(`ArtistController`
javadoc). 즉 기존 계약을 깨는 게 아니라, 구현 전에 계약을 고치는 시점이다.

## 결정

### D1. 별칭 테이블을 신설하고 검색 대상을 그쪽으로 옮긴다

`artist_aliases(artist_seq, language_code, alias)` 와
`group_aliases(group_seq, language_code, alias)` 를 만든다. §5.2 는 두 테이블의
`alias` 만 본다.

**표시 이름은 `users.nickname` 고정이다.** 별칭은 찾는 데만 쓰고 응답에 싣지 않는다.

찾기와 보여주기를 갈라 두는 이유는 범위다. 공통 아티스트 요약(API 상세 명세 README
§3.5)의 `name` 은 §4.6·§4.7·§5.1·§5.3·§5.5·§5.10·§6.3·§7.1·§7.2·§11.1·§11.2·
§11.5·§11.6·§11.9 가 같은 모양으로 쓴다. 표시 이름 해석을 별칭으로 옮기면 그 전부가
언어 협상(Accept-Language)과 폴백 규칙을 갖게 되고, 별칭이 비어 있는 아티스트마다
이름이 사라지는 경로가 생긴다. 검색 하나를 고치려고 그 전부를 흔들 이유가 없다.

대가는 명확하다 — 영어 사용자가 "Karina" 로 검색해도 결과에는 "카리나" 가 뜬다.
그건 의도된 상태다.

### D2. 두 테이블로 나눈다 — 하나로 합치지 않는다

`artist_aliases` 하나로는 그룹 별칭을 담을 수 없다. `artist_seq` FK 가 가리키는 것은
멤버지 그룹이 아니다. 검토한 대안은 셋이었다.

| 안 | 문제 |
|---|---|
| 폴리모픽 (`target_type` + `target_seq`) | FK 를 못 건다. 이 스키마는 모든 참조에 FK 를 건다 |
| 그룹 별칭을 멤버별로 복제 | 별칭 하나 고치는 데 N 행 UPDATE. 멤버 추가 시 누락 |
| **테이블 둘** | 채택 |

결정적인 이유는 FK 가 아니라 **판정**이다. §5.2 는 "이 매치가 그룹 매치였는가" 를
알아야 그룹 멤버를 확장해 넣고, 그렇게 들어온 멤버를 본인 매치보다 뒤로 정렬할 수
있다. 테이블이 갈려 있으면 그 사실이 조회 구조에서 공짜로 나온다. 한 테이블에
넣으면 같은 정보를 칼럼으로 다시 표현해야 한다.

### D3. `language_code` 는 저장 구분일 뿐, 검색에 쓰지 않는다

언어로 필터링하지 않는다. 한국어 UI 사용자도 "aespa" 를 영문으로 치는 일이 흔해서,
요청 언어로 거르면 **오히려 안 나온다**. `language_code` 는 운영자가 별칭을 언어별로
정리해 넣고 화면에서 훑어보기 위한 칸이다.

같은 이유로 `UNIQUE(대상, language_code)` 를 걸지 않는다 — 한 언어에 표기 변형이
여럿이다(`aespa`·`æspa`, 활동명·본명). 중복 입력도 막지 않는다. §5.2 가 `artistSeq`
로 중복을 제거하므로 결과가 겹치지 않는다.

### D4. `ILIKE` 를 쓴다 — pg_trgm 유사도를 버린다

구 §5.2 는 pg_trgm 유사도 검색이라 오타가 보정됐다(`카리다` → `카리나`). 그것을
`alias ILIKE '%q%'` 로 바꾼다.

**오타 보정을 잃는다.** 대신 얻는 것은 결정적인 순서다. 유사도 점수로 정렬하면 별칭이
늘어날 때 같은 질의의 순서가 흔들리는데, 자동완성은 순서가 바뀌면 바로 티가 난다.
정렬을 명시 규칙으로 고정한다:

```
본인 별칭 매치 전부  →  그룹 확장 멤버
  각 덩어리 안에서: 완전 일치 → 접두 일치 → 별칭 길이 ASC
                   → subscriber_count DESC → artistSeq ASC
```

구 §5.9 의 "1~2자 접두 / 3자 이상 trgm" 2단 전략도 함께 버린다. 두 전략이 경계에서
서로 다른 결과 집합을 주면 3글자째를 입력하는 순간 목록이 통째로 갈아엎어진다.

`ILIKE` 는 대소문자를 무시하므로 D3 의 다국어 요구와 맞물린다 — `Karina`·`karina`·
`KARINA` 가 같다.

### D5. pg_trgm 을 유지한다 — pg_bigm 을 채택하지 않는다

pg_trgm 은 3글자 조각 기반이라 **한글 2음절 질의(`카리`)에서 트라이그램이 하나도
나오지 않아 인덱스를 못 탄다.** 2글자 조각을 쓰는 pg_bigm 은 바로 그 약점을 겨냥해
만들어진 확장이고, 지적 자체는 정확하다.

그래도 채택하지 않는다.

1. **이 규모에서 측정에 안 잡힌다.** 아티스트가 수백, 별칭이 천 단위다. 테이블 전체가
   한두 페이지라 플래너가 인덱스가 있어도 순차 스캔을 고른다.
2. **pg_bigm 은 contrib 이 아니다.** 서드파티라 DB 이미지에 따로 설치해야 하는데,
   pg_trgm 은 이미 `docs/db/manual-prereq.sql` 과 인프라 라인 `configmap-init.yaml`
   이 소유하고 있다. 확장을 추가하면 인프라 파트 티켓이 물린다.
3. **실패 모드가 나쁘다.** 인덱스 changeSet 이 `precondition onFail:HALT` 구조라
   (0012-05·06), 한 환경에서만 설치가 빠져도 마이그레이션 전체가 멈춘다.
4. 1글자 질의는 bigm 도 인덱스를 못 탄다. 자동완성 첫 글자는 어느 쪽이든 풀스캔이다.

별칭이 만 단위로 커지면 재검토한다. 그때 바꾸는 것은 `CREATE INDEX` 한 줄이라 이
결정이 잠그는 것이 없다.

### D6. 검색과 자동완성을 §5.2 하나로 합친다

원본 v0.7(R4)이 "응답을 최소화" 하려고 §5.2 확정 검색과 §5.9 자동완성으로 나눴다.
되돌린다.

두 응답의 차이가 `isSubscribed` **한 칸**이었다. 그 한 칸 때문에 경로가 둘이면
온보딩 §3.2 가 어느 쪽을 부르는지도 갈리고, 매칭 전략을 고칠 때 두 곳을 고쳐야 한다.
남기는 경로는 `/artists/search` 다 — §3.2 가 이 경로를 재사용한다고 명세에 적혀 있어,
반대로 남기면 온보딩 계약까지 바뀐다.

### D7. 별칭은 소프트 삭제를 따라가지 않는다

아티스트·그룹을 소프트 삭제해도 별칭 행을 건드리지 않는다. §5.2 가 조회 시
`is_deleted = FALSE` 조인으로 거른다.

별칭에 `is_deleted` 를 또 두면 "아티스트는 살아 있는데 별칭만 죽은" 상태가 생기고,
그걸 정상으로 취급하는 분기가 조회마다 하나씩 늘어난다. 삭제 연쇄로 행을 지우면
복구가 불가능해진다.

어드민이 직접 지우는 것(어드민 §3.5.9)은 **하드 삭제**이며 위와 별개 동작이다. 그
API 는 프로젝트 기능이 아니라 시연 편의용이라 수정·삭제까지 열어 뒀다.

## 결과

**얻는 것**

- 언어를 추가하는 데 스키마 변경이 없다 — 행을 넣으면 된다.
- 그룹 검색이 구조에서 나온다. `group_aliases` 매치 = 그룹 확장, 판정이 한 곳이다.
- 같은 질의가 항상 같은 순서를 준다.
- 어드민 §3.5.1 목록 검색은 그대로 `users.nickname` 을 본다(`gin_users_nickname`
  유지) — 운영자는 등록한 이름으로 찾는다. 팬 앱과 어드민의 검색 대상이 갈린다.

**잃는 것**

- **오타 보정**(D4). `카리다` 는 0건이다.
- **별칭을 채워야 검색이 동작한다.** 빈 테이블이면 결과가 항상 0건이다. 그래서 어드민
  별칭 CRUD 와 시드가 검색 API 와 같은 범위에 들어간다.
- 한글 2음절 질의는 인덱스를 못 탄다(D5). 지금 규모에서는 무해하다.

**구현 시 주의**

조회는 **네이티브 쿼리 + `ILIKE`** 로 쓴다. JPQL 에는 `ILIKE` 가 없어
`lower(alias) like lower(?)` 로 쓰게 되는데, 그러면 `alias` 에 걸린
`gin_trgm_ops` 인덱스에 **붙지 않는다** — 인덱스가 걸린 식과 조회하는 식이 다르다.
`gin_trgm_ops` 는 트라이그램 추출 시 스스로 소문자로 내리므로 원본 칼럼 인덱스가
이미 대소문자를 무시한다.

`q` 에 `null` 을 넘기지 않는다. Postgres 가 타입 없는 `null` 을 `bytea` 로 추론해
`function lower(bytea) does not exist` 로 죽는다 — `ArtistRepository.search` 가 이미
밟은 함정이다(2026-09-13 운영 500). 빈 `q` 는 `'%%'` 가 되어 전체 조회가 되므로
`400 INVALID_PARAMETER` 로 막는다.

## 대안

**별칭을 표시에도 쓴다 (전면 다국어)** — Accept-Language 로 이름을 고른다. 진짜
다국어는 이쪽이지만 15개 응답의 계약이 바뀌고, 별칭이 없는 아티스트의 폴백 규칙이
필요하다. 검색이 먼저 필요했고, 이 ADR 은 그 길을 막지 않는다 — 표시 해석을 나중에
얹어도 `artist_aliases` 는 그대로 쓴다.

**`users.nickname` 에 영문명을 덧붙여 저장** (`카리나 (Karina)`) — 스키마 변경이
없지만 화면에 괄호가 그대로 노출되고, 언어가 셋이 되면 무너진다.

**전문 검색 엔진(Elasticsearch 등)** — 오타 보정·형태소·동의어를 전부 얻지만, 운영할
인프라가 아티스트 수백 건을 위해 늘어난다. 규모가 근거를 주지 않는다.
