# ADR-0015. 조회수는 Redis 에 모아 20분마다 집계하고, 랭킹은 그 집계로 굴린다

- 상태: 승인
- 일자: 2026-09-21
- 관련: API 명세 §6.1·§8.5, ADR-0009(1 레플리카), ADR-0011(Redis 단명 상태), `S15P21D104-130`

## 컨텍스트

`participation_videos.view_count` 는 **지금까지 한 번도 증가한 적이 없다.** 게시(§8.8)가 0 으로
넣는 것이 전부이고, 조회 이벤트 API(§8.5)는 명세만 있고 구현이 없었다. 그 결과:

- §6.1 HOT 랭킹은 `view_count × 0.5^(age/H)` 로 점수를 내는데 **모든 영상의 조회수가 0** 이라
  사실상 게시 시각 역순이다.
- §8.1 피드의 추천 점수도 `view_count` 를 재료로 쓴다.

조회수를 채우려 할 때 순진한 방법은 조회 이벤트마다 `UPDATE ... SET view_count = view_count + 1`
이다. 재생마다 쓰기가 한 번 발생하고, 인기 영상 한 행에 쓰기가 몰려 행 잠금이 직렬화된다.
조회수는 **정확도가 1 단위로 중요하지 않은 값**이라 그 비용을 치를 이유가 없다.

동시에 랭킹 공식에도 문제가 있었다. 감쇠의 기준이 **게시 시각**인 이유는 다른 시간축이 없어서다 —
`view_count` 는 누적 카운터라 개별 조회가 **언제** 발생했는지가 DB 에 없다. 그래서 감쇠는
"이 영상이 얼마나 오래된 게시물인가" 를 재고, **오래된 영상은 지금 아무리 떠도 올라올 수 없다.**
"실시간 인기" 자리에서 이것은 요구와 반대다.

## 결정

**조회 이벤트는 Redis HASH 에 누적하고, 20분 주기 배치가 DB 반영·시간 버킷·랭킹 갱신을 한 번에
한다. 랭킹 점수에서 시간 감쇠를 걷어내고 그 버킷을 쓴다.**

### 키 구조

```
view:video:pending              HASH    videoSeq → 미반영 조회수
view:video:processing:{ts}      HASH    집계 중인 스냅샷
view:video:processing:index     LIST    미완료 {ts} — 재처리 진입점
view:video:bucket:{ts}          HASH    그 구간에 발생한 조회수      TTL 6h
view:video:bucket:index         LIST    최신 {ts} 가 앞              LTRIM 12
view:flush:applied:{ts}         STRING  멱등 마커 (SETNX)           TTL 24h

rank:video:current              STRING  버전 포인터
rank:video:{version}            ZSET    score = rank(1-base)        TTL 2h
rank:video:{version}:delta      HASH    videoSeq → rankDelta        TTL 2h
rank:video:versions             LIST    최신 version 이 앞           LTRIM 8
```

누적에 ZSET 이 아니라 HASH 를 쓰는 것은 **정렬이 필요 없기 때문**이다. `HINCRBY` 가 원자적이라
동시 요청이 서로를 덮지 않는다. 정렬이 필요한 것은 최종 랭킹 하나뿐이고 그것만 ZSET 이다.

### 집계 흐름

```
0) processing:index 에 남은 {ts} 가 있으면 그것부터 처리한다
1) RENAMENX  view:video:pending → view:video:processing:{ts}
2) SETNX     view:flush:applied:{ts}
             성공 → DB 미반영 → 3) 실행 / 실패 → 이미 반영됨 → 건너뛴다
3) DB 일괄 반영 (native 한 문장)
4) 버킷 HINCRBY + TTL + bucket:index LPUSH/LTRIM
5) 랭킹 재계산 · ZSET·delta 적재 · 포인터 이동
6) DEL processing:{ts} + index LREM
```

**`RENAME` 이 아니라 `RENAMENX` 다.** `RENAME` 은 대상 키가 이미 있으면 덮어쓴다 — 재처리가 밀려
같은 `{ts}` 의 `processing` 이 남아 있는 상태에서 rotate 하면 **그 안의 조회수가 통째로 사라진다.**
`RENAMENX` 가 실패하면 rotate 하지 않고 남은 것부터 처리한다.

**`pending` 키가 없으면(20분간 조회 0건) 전부 건너뛴다.** Redis 에 빈 키는 존재하지 않으므로
`RENAME` 계열이 예외를 낸다 — §5.1 `ArtistRankingSnapshot` 이 같은 함정을 밟았다. 이때 버킷은
만들지 않고 랭킹만 다시 돈다(감쇠는 없지만 최근·증감 항이 바뀐다).

**DB 반영은 영상별 `UPDATE` N번이 아니라 한 문장이다.**

```sql
update motif_core.participation_videos v
   set view_count = v.view_count + d.delta
  from (select unnest(:seqs) as seq, unnest(:deltas) as delta) d
 where v.video_seq = d.seq
```

`is_deleted` 를 조건에 걸지 않는다 — `view_count` 는 **누적 사실의 기록**이고 노출 여부는 조회
쿼리가 따로 거른다. 신고 기각 등으로 되살아났을 때 숫자가 맞아야 한다.

### 멱등은 마커 하나로 닫는다

DB 와 Redis 는 한 트랜잭션에 묶을 수 없다. 요구된 흐름(`processing` 삭제가 맨 마지막)만으로는
**"DB 반영 성공 → Redis 후처리 전 종료"** 에서 재시작 시 이중 가산이 난다.

`SETNX view:flush:applied:{ts}` 가 "이 구간은 DB 에 넣었다" 는 유일한 사실이다. 3~6 어디서 죽어도
재처리가 2) 에서 걸러진다.

Redis 자체를 잃으면 마커도 사라지지만 **그때는 `pending`·`processing` 도 함께 사라져 재처리할
대상이 없다.** 실질 공백이 생기지 않는다.

### ShedLock 을 도입하지 않는다

core-api 는 1 레플리카다(ADR-0009). 기존 배치들이 락 없이 도는 근거는 *"전량 재계산이라 중복
실행돼도 결과가 같다"* 인데, **조회수 집계는 누적 연산이라 그 근거가 그대로 적용되지 않는다.**
대신 `RENAMENX` 의 원자성이 rotate 를 한 쪽만 성공시키고, 마커가 DB 이중 가산을 막는다. 둘로
닫히므로 의존성과 ADR 을 하나 더 늘리지 않는다. 다중화하는 시점에 다시 본다.

### 버킷을 시간 산술로 찾지 않는다

`{ts}` 는 **사람이 읽는 이름표일 뿐**이고, "최근 1시간" 은 `bucket:index` 리스트의 **앞 3개**다.
그 이전 1시간은 다음 3개다.

이렇게 두면 세 가지가 한꺼번에 없어진다.

- 스케줄러가 `fixedDelay` 라 벽시계에 정렬되지 않는 문제 — 키를 산술로 만들지 않으므로 무관하다
- 집계 주기와 조회 구간이 나눠떨어져야 하는 제약 — 설정이 시간이 아니라 **개수**가 된다
- 조회 0건이라 건너뛴 구간의 처리 — 리스트에 안 들어가므로 자연히 무시된다

대가로 **조회가 전무한 구간이 있으면 "최근 3개" 가 시간상 1시간보다 길어진다.** 서비스 전체
조회가 20분간 0건인 상황에서만 일어나고, 그때는 순위가 어차피 움직이지 않는다.

### 랭킹 점수 — 감쇠를 걷어내고 세 항을 쓴다

```
tScore = log10(1 + totalViews)    / log10(1 + T0)
rScore = log10(1 + recentViews1h) / log10(1 + R0)
dRel   = (recentViews1h − previousViews1h) / (previousViews1h + K)
dScore = 0.5 + 0.5 × clamp(dRel / D0, −1, +1)

score  = Wt·tScore + Wr·rScore + Wd·dScore        (기본 0.3 / 0.5 / 0.2)
```

**세 항이 서로 다른 것을 잰다** — 누적 규모(절대) · 최근 규모(절대) · 모멘텀(상대). 절대 증감을
따로 넣지 않는 것은 `recentViews1h` 가 이미 최근의 절대량이라 같은 신호가 두 번 가산되기 때문이다.

**시간 감쇠를 뺐다.** 신선도는 `rScore`·`dScore` 가 70% 로 맡는다. 감쇠를 남기면 오래된 영상은
지금 아무리 떠도 계수에 눌려 올라올 수 없는데, 그것이 이 자리의 요구와 반대다. 윈도우 기반
트렌딩은 감쇠 대신 윈도우를 쓰는 정당한 계열이다.

**증감은 절대값이 아니라 기존 값 대비다.** `+100` 이 직전 50 위에서 난 것과 5,000 위에서 난 것은
다른 사건이다. 다만 순수 비율은 **작은 분모에서 폭발한다** — `0 → 3` 이 `1000 → 2000` 을 이긴다.
분모의 완충 상수 `K` 가 그 지점을 막는다(`K = 10` 이면 `0 → 3` 의 `dRel` 은 0.3 에 그친다).

**정규화 기준은 그 틱의 최대값이 아니라 고정 상수 `T0`·`R0`·`D0` 다.** 최대값으로 나누면 점수가
집단에 상대적이 되어,

- 다른 영상이 떡상했다는 이유만으로 내 점수가 내려간다
- 1위 영상이 삭제되면 전원의 점수가 움직인다
- 같은 입력이 다른 순위를 낳아 **나중에 재현·검증할 수 없다**

앞의 둘은 `rankDelta` 를 응답에 싣는 순간 **아무도 아무 것도 하지 않았는데 뜨는 거짓 변동**이
된다. 고정 기준이면 점수가 절대값이고, 로그에 찍어 둔 값이 나중에 그대로 검증된다.

`tScore`·`rScore` 는 1 로 자르지 않는다. 기준을 넘는 영상이 전부 같은 값이 되면 최상위권의
변별이 사라진다 — 순위만 쓰므로 범위가 `[0,1]` 일 필요가 없다.

**모집단은 `view_count > 0`** 이다. 조회가 한 번이라도 발생한 뒤부터 랭킹에 들고, 한 번 들어온
영상은 조용해져도 남아 최근·증감 항이 떨어지면서 뒤로 밀린다. 적재는 상위 `keep`(기본 500)개로
자른다 — **점수 임계로 자르지 않는다.** 고정 기준 정규화라 임계를 둘 수는 있지만, 트래픽이 적은
시간대에 목록이 통째로 비는 편이 더 나쁘다.

### 순위 변동은 배치가 계산해 둔다

`rank:video:versions` 에서 3틱 전(=1시간 전) 버전의 rank map 을 읽어 `직전 − 현재` 를 delta HASH
에 적는다. 조회 시점에 이전 버전을 통째로 읽으면 **요청마다** 스냅샷 전량을 읽게 된다.

이전 버전에 없던 영상은 값을 적지 않는다(= `null`, 신규 진입). 랭킹이 처음 만들어진 틱은 전원
`0` 으로 심어 `null` 을 진짜 신규 전용으로 남긴다(§5.1 과 같은 판단).

**버전 키 TTL 을 15분에서 2시간으로 올린다.** 대비 대상이 1시간 전 버전이라 보존이 그보다 짧으면
**`rankDelta` 가 조용히 전원 `null` 이 된다** — 예외도 로그도 남지 않는 종류다.

### 조회 API 는 fail-open 이다

Redis 가 죽으면 예외를 삼키고 202 를 준다. 영상은 정상 재생되는데 조회수 집계 실패로 클라이언트가
에러를 보는 것이 더 나쁘다. ADR-0011 의 프로필 이미지가 fail-closed 인 것과 반대인데, 그쪽은
실패했을 때 **사용자가 무엇을 해야 할지 알 수 있는** 실패였고 이쪽은 아니다.

존재하지 않는 `videoSeq` 도 검증하지 않는다 — 조회 이벤트마다 DB 를 확인하면 집계를 Redis 로 뺀
의미가 없다. 없는 키는 3) 의 `UPDATE` 가 0행으로 버리고, 랭킹 모집단은 DB 에서 나오므로 순위에도
오르지 않는다.

## 결과

**얻는 것**

- 조회 이벤트가 DB 쓰기를 만들지 않는다. 인기 영상 한 행에 쓰기가 몰리지 않는다.
- 개별 조회의 **발생 시각**이 생긴다. 랭킹이 "언제 게시됐나" 가 아니라 "지금 얼마나 보고
  있나" 를 재게 된다.
- `view_count` 는 계속 DB 가 정본이다. Redis 를 잃어도 누적 조회수는 살아남는다.

**잃는 것 · 감수하는 것**

- **반영 지연이 최대 20분이다.** `viewCount` 가 즉시 오르지 않는다(202 의 뜻이 그것이다).
  시연에서 순위가 움직이는 것을 보여주려면 `interval` 을 내려야 하는데, 버킷이 **개수** 기반이라
  `recent-buckets` 를 함께 올려야 한다(`1m` + `60`). 한쪽만 고치면 "최근 1시간" 이 조용히
  "최근 3분" 이 된다.
- **Redis 를 잃으면 최대 20분치 조회수와 버킷 전량이 사라진다.** 버킷이 없으면 `rScore`·`dScore`
  가 0 이라 **랭킹이 약 1시간 동안 누적순으로 회귀한다.** 고장이 아니라 예상 동작이다.
- **어뷰징에 무방비다.** 서버는 클라이언트가 보낸 `count` 를 믿는다. 랭킹이 조회수로 굴러가므로
  조작하면 순위가 움직인다. 현재 방어는 영상당 `count` 상한 하나뿐이고, 1회 인정 기준(원본 §16 #3)
  은 여전히 미결이다.
- **`T0`·`R0`·`D0` 와 가중치는 실측 없이 정한 값이다.** 설정이라 재배포 없이 고칠 수 있게 두었다.
  순위가 기대와 다르면 여기를 먼저 본다.
- **누적 항에 감쇠가 없다.** `totalViews` 는 줄지 않으므로 오래된 영상은 가만히 있어도 `tScore`
  몫(30%)을 영원히 받는다. 검산에서는 신규 급상승이 이기지만, 순위가 굳어 보이면 `Wt` 를 먼저
  의심한다.

## 대안

| 안 | 버린 이유 |
|---|---|
| 조회마다 DB `UPDATE` | 재생마다 쓰기. 인기 영상 한 행에 잠금이 직렬화된다 |
| 누적을 ZSET 으로 | 정렬이 필요 없다. 정렬이 필요한 것은 최종 랭킹 하나뿐이다 |
| Lua 로 `HGETALL` + `DEL` 원자화 | 큰 HASH 에서 블로킹한다. `RENAMENX` 는 O(1) 이고 같은 원자성을 준다 |
| 플러시 이력 테이블로 멱등 | 진짜 멱등이지만 changeSet + DB 명세 갱신이 붙는다. "20분마다 한 행 늘고 며칠 뒤 지우는 표" 라 ADR-0011 이 경계하는 모양이다 |
| ShedLock | 1 레플리카에서 `RENAMENX` + 마커로 닫힌다. 의존성과 ADR 을 하나 더 늘리지 않는다 |
| 벽시계 정렬(cron) 버킷 | 리스트 인덱스가 드리프트·건너뜀·나눠떨어짐을 한꺼번에 없앤다 |
| 그 틱 최대값으로 정규화 | 다른 영상의 등락이 내 순위를 바꾸고, `rankDelta` 에 거짓 변동이 뜬다 |
| 순수 증가율(`recent/prev`) | 작은 분모에서 폭발한다 — `0 → 3` 이 `1000 → 2000` 을 이긴다 |
| 시간 감쇠 유지 | 오래된 영상이 지금 떠도 올라올 수 없다. 이 자리의 요구와 반대다 |
| 점수 임계로 랭킹 절단 | 트래픽이 적은 시간대에 목록이 통째로 빈다. 개수 상한은 결과가 예측된다 |
