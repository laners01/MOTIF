# 영상 전달 방식 — 인계 문서

**대상: Android · Backend 파트 전원.**
PoC 로 정한 내용과 각 파트가 무엇을 구현해야 하는지를 담는다.

- 결정문: [ADR-0010](../adr/0010-video-delivery.md) — **이 문서의 모든 값은 ADR 을 가리킨다**
- 측정 상세: [video-delivery-results.md](video-delivery-results.md)
- 판정 기준: [video-delivery.md](video-delivery.md)

## 0. 한 장 요약

| | |
|---|---|
| **무엇을 정했나** | 영상을 화질 2종으로 만들어 서빙하고, 재생 중 네트워크에 따라 화질을 자동 전환한다 |
| **왜** | 원본(평균 3.35Mbps)은 느린 네트워크에서 재생이 끊긴다. 1.5Mbps 구간에서 **누적 170초** 멈춘다 — 재생 시간(144초)보다 길다 |
| **효과** | 재생 중 대역폭이 무너져도 **멈춤 0회**, CDN 전송량은 고화질 고정 대비 **64%** |
| **Android** | HLS 재생 + 미리받기(앞 2개 × 1.5초) + 썸네일 선행 로드 |
| **Backend** | 렌디션 2종 인코딩 + HLS 패키징 + 썸네일 추출 (합성 직후 동기, 약 10초) |

## 1. 용어

읽기 전에 이것만 알면 된다.

| 용어 | 뜻 |
|---|---|
| **비트레이트** | 영상 1초를 재생하는 데 필요한 데이터 양. 높을수록 화질이 좋고 무겁다 |
| **렌디션** | 같은 영상의 다른 화질 사본 (720p / 480p) |
| **TTFF** | Time To First Frame. 스와이프하고 **첫 그림이 뜰 때까지** 걸리는 시간 |
| **스톨 / 재버퍼** | 재생 **도중** 멈추는 것. 유튜브에서 빙글빙글 도는 그것 |
| **프리페치** | 다음 영상을 미리 받아두기 |
| **N · T** | 프리페치 설정. **N** = 다음 몇 개, **T** = 각각 앞 몇 초 |
| **ABR** | Adaptive Bitrate. 네트워크에 맞춰 **화질을 자동 전환**하는 것 |
| **HLS** | ABR 을 구현하는 표준 방식. 영상을 조각으로 나눠 조각 단위로 화질을 바꾼다 |
| **moov** | MP4 안의 목차(색인). 파일 **앞**에 있어야 바로 재생이 시작된다 |
| **GOP** | 키프레임 간격. 키프레임은 혼자 완성된 화면이라 **여기서만 조각을 자를 수 있다** |
| **egress** | 서버에서 나가는 트래픽. **CDN 요금이 붙는 대상** |

## 2. 왜 이 일을 했나

### 문제

앱은 영상을 위로 스와이프하며 본다. 정해지지 않은 것이 둘이었다.

1. **다음 영상이 얼마나 빨리 뜨는가** — 안 뜨고 빙글빙글 돌면 앱이 구리게 느껴진다
2. **그 대가로 트래픽을 얼마나 쓰는가** — 미리 받아두면 빨라지지만 안 볼 영상까지 받는다

감으로 정하면 나중에 "느린데요" 또는 "요금 많이 나오는데요" 를 듣고 다시 한다.

### 그리고 실측에서 더 큰 문제가 나왔다

팀이 준 영상 31개를 조사해보니 **설계 가정과 달랐다.**

| | 설계 가정 | 실측 |
|---|---|---|
| 해상도 | 720p | **1080p 위주** (31개 중 22개) |
| 비트레이트 | 2.5Mbps | **평균 3.35Mbps**, 최대 5.88Mbps |

**31개 중 4개는 5.88Mbps 라 4Mbps 회선에서 실시간 재생이 물리적으로 불가능하다.**
요구 속도가 회선 속도보다 크면 방법이 없다.

## 3. 어떻게 확인했나

### 안드로이드 없이 측정했다

```
첫 화면 = [네트워크로 받는 시간] + [폰이 영상 푸는 시간]
            ↑ 전략이 바꾸는 항        ↑ 어떤 전략이든 동일
```

폰이 푸는 시간은 전략과 무관하게 같으므로 **순위는 네트워크 항에서만 갈린다.**
그래서 노트북 안에 가짜 환경을 만들어 쟀다.

- **가짜 서버** — nginx
- **가짜 느린 네트워크** — `tc netem` 으로 대역폭·지연을 조인다
- **가짜 사용자** — 30개 피드를 스와이프하는 시뮬레이터 (3초 스킵 40% / 절반 30% / 완시청 30%)

| 프로파일 | 대역폭 | 지연 |
|---|---|---|
| Wi-Fi | 100Mbps | 10ms |
| LTE 양호 | 20Mbps | 50ms |
| LTE 약함 | 4Mbps | 100ms |
| 매우 느림 | 1.5Mbps | 300ms |

### 측정 도구가 정확한지부터 검증했다

서버가 기록한 "보낸 바이트" 와 시뮬레이터가 기록한 "받은 바이트" 를 대조했다.

> **오차 0.00%** (허용 기준 ±5%)

이게 안 맞으면 아래 수치는 전부 무효다. 요청 URL 에 `?s=<실행id>` 를 붙여
실행별로 갈라냈다.

### 이 측정의 한계

- `tc netem` 은 **고정 대역폭 + 고정 지연**만 재현한다. 지터·패킷 손실·핸드오버는 없다
- ABR 판단은 ExoPlayer 휴리스틱의 **모형**이다. 라이브러리 자체가 아니다
- 세션 표본이 조합당 1~2회다
- **절대값 예측이 아니라 전략 간 순위 비교용이다.** "실제 LTE 에서 정확히 344ms" 가
  아니라 "같은 조건에서 A 가 B 보다 낫다" 가 결론이다

## 4. 측정 결과

모든 수치는 **14개 영상을 본 한 세션**(재생 시간 144초) 기준이다.

### 4.1 원본 그대로는 안 된다

| 네트워크 | 원본 (3.35Mbps) | 720p (0.78Mbps) | 480p (0.47Mbps) |
|---|---|---|---|
| LTE 양호 20Mbps | 0회 | 0회 | 0회 |
| LTE 약함 4Mbps | 5회 / 6초 | **0회** | 0회 |
| 매우 느림 1.5Mbps | 10회 / **170초** | 3회 / 6초 | 1회 / 0초 |

1.5Mbps 에서 **누적 170초 멈춘다** — 재생 시간 144초보다 길다.

**전송량도 크게 준다.**

| 화질 | 시청 영상 1개당 | 세션 합계 |
|---|---|---|
| 원본 | 4.04MB | 56.6MB |
| **720p** | **1.22MB** | **17.1MB** (원본의 **30%**) |
| 480p | 0.72MB | 10.1MB |

### 4.2 재생 중 네트워크가 무너지면 — ABR 이 필요한 이유

40초 재생 후 20Mbps → 1.5Mbps 로 떨어뜨렸다. **지하철 진입 같은 상황이다.**

| | 전송량 | 멈춤 |
|---|---|---|
| 480p 고정 | 10.1MB | 0회 |
| 720p 고정 | 17.1MB | 2회 / 5초 |
| **ABR** | **11.0MB** | **0회** (전환 2회) |

- **720p 고정**은 화질을 못 바꾸니 끝까지 버티다 끊긴다
- **480p 고정**은 안 끊기지만 붕괴 전 20Mbps 구간의 화질을 통째로 포기한 대가다
- **ABR** 은 붕괴 전 720p, 붕괴 후 480p — **화질과 안정성을 모두 취하고 전송량은 720p 고정의 64%**

**영상을 열 때 화질을 한 번 고르는 방식으로는 이 상황을 커버할 수 없다.**
이미 영상을 열고 재생 중이기 때문이다.

노출 빈도도 작지 않다 — 한 세션에서 **10초 이상 본 영상은 14개 중 4개뿐이지만
시청 시간의 75%** 를 차지한다. 붕괴는 대부분 "긴 영상 재생 중" 에 온다.

### 4.3 미리받기(프리페치) 설정

1.5Mbps / 720p 기준:

| 정책 | 전송량 | 낭비 | 멈춤 |
|---|---|---|---|
| 없음 | 16.9MB | 0% | 6회 / 10초 |
| **N=2 × 1.5초** | 17.1MB | 1.5% | **3회 / 6초** |
| N=3 × 1.0초 | 17.1MB | 1.5% | 3회 / 7초 |
| N=2 × 전체 | 30.0MB | 10.6% | 1회 / 1초 |

- `N=2×1.5초` 와 `N=3×1.0초` 는 **받는 총량이 같고**(3초 분량) 결과도 사실상 같다
- `N=2 전체` 는 멈춤이 가장 적지만 전송량 1.8배·낭비 7배. **그 이득은 ABR 과 중복된다**
- **프리페치는 "빨리 뜨게 하는 장치" 가 아니라 "안 끊기게 하는 장치" 다.**
  네트워크에 여유가 있으면 효과가 정확히 0 이다

### 4.4 첫 화면 뜨는 시간(TTFF)

| 네트워크 | 원본 | 720p | 480p |
|---|---|---|---|
| Wi-Fi | 67ms | 56ms | 58ms |
| LTE 양호 | **344ms** | **289ms** | 290ms |
| LTE 약함 | 1041ms | 760ms | 696ms |

**목표 200ms 에 미달이다.** 그리고 **화질을 낮춰도 거의 안 준다**(344 → 289ms).
첫 프레임에 필요한 바이트가 작아 통신 왕복 시간이 지배하기 때문이다.

**→ 이 문제는 썸네일로 푼다.** §4.5

### 4.5 썸네일

| | 전송 바이트 | LTE 양호 |
|---|---|---|
| 영상 첫 프레임까지 | 671KB | ~290ms |
| **썸네일** | **20~40KB** | **~30ms** |

영상이 뜨기 전 썸네일을 먼저 보여주면 **체감 대기가 사실상 사라진다.**
DB(`thumbnail_key`)·API(`thumbnailUrl`)·용도(첫 프레임 전 플레이스홀더, 회의 확정 R2)가
**모두 이미 있다.** 스키마·명세 변경 없음.

### 4.6 영상 파일 자체는 문제 없었다

- **moov 31개 전부 파일 앞**에 있다 → faststart 재처리 불필요
- 다만 **GOP(키프레임 간격)가 2.03~8.34초로 제각각**이고 화질 간에 안 맞는다.
  ABR 을 하려면 이걸 고정해야 한다 (§6)

## 5. Android 구현 방향

### 5.1 HLS 재생 + ABR

```
백엔드가 주는 것: 재생목록 주소 (master.m3u8)
플레이어가 하는 것: 조각마다 속도를 재고 알아서 화질 선택
```

**판단 로직은 직접 짜지 않는다.** Media3(ExoPlayer)에 이미 들어 있다.

동작 원리(참고):

```
조각 하나 받을 때마다 → "몇 바이트를 몇 초에" = 대역폭 표본
다음 조각 요청 직전   → 추정 대역폭 × 0.7 이하인 가장 높은 화질 선택
                       버퍼가 얕으면 안 올리고, 마르면 즉시 최저로
```

**확인 요청 ①**: Media3 의 **fMP4 + `EXT-X-BYTERANGE`** 재생 지원 범위.
백엔드가 이 방식으로 패키징한다(화질당 파일 1개 유지 — §6.2).
표준(RFC 8216) 기능이나 라이브러리 지원 확인이 필요하다.
**안 되면 ADR 을 개정한다.**

### 5.2 프리페치 — 앞 N개 × 첫 T초

```
지금 보는 중   다음         그다음       그다음
   [3번]   →  [4번]        [5번]       [6번]
             앞 1.5초      앞 1.5초     안 받음
```

**채택값: `N=2, T=1.5초`**

- ❌ **영상을 통째로 미리 받지 말 것.** 전송량 1.8배·낭비 7배다
- Media3 `DefaultPreloadManager` 가 이 기능을 제공한다
- 이 값은 **출발값**이다. 출시 후 계측으로 재조정한다(§5.4)

**확인 요청 ②**: `DefaultPreloadManager` 와 HLS 조합 호환성

### 5.3 썸네일 선행 로드

```
피드 목록 로드 시 썸네일 함께 받아둠
   → 스와이프 즉시 썸네일 표시
   → 영상 첫 프레임 준비되면 교차 전환(cross-fade)
```

- **스와이프 시점에 받으면 효과가 반감된다.** 그것도 왕복이 들기 때문이다
- 목록 응답에 `thumbnailUrl` 이 **이미 들어 있다**

**확인 요청 ③**: 현재 `thumbnailUrl` 을 실제로 플레이스홀더로 쓰고 있는지,
쓴다면 **언제 받는지**(목록 로드 시 vs 스와이프 시)

### 5.4 계측 심기 — 이게 없으면 위 값들을 검증할 수 없다

출시 버전에 다음을 기록해 보낸다.

| 항목 | 용도 |
|---|---|
| 재버퍼 발생 횟수·누적 시간 | 화질 사다리가 맞았는지 판정 |
| 발생 시점의 추정 처리량 | 실사용 대역폭 분포 파악 |
| 선택된 화질 | ABR 이 제대로 고르는지 |
| 세션당 시청 영상 수 / 이탈 지점 | 프리페치 낭비율 실측 (현재는 가정값) |

**마지막 항목이 중요하다.** 현재 낭비율(1.5~10.6%)은 "스와이프당 5% 이탈" 이라는
가정 위에서 나온 값이다. 실제 이탈률은 운영 데이터로만 알 수 있다.

## 6. Backend 구현 계획

### 6.1 워커 파이프라인

```
AI 합성 완료 (영상 1개)
   ↓
① 렌디션 인코딩  720p / 480p
② HLS 패키징     화질별 fMP4 + 재생목록
③ 썸네일 추출    1.5초 지점
④ S3 업로드
```

**합성 직후 동기 처리한다. 배치로 미루지 않는다.**

실측 비용 (60초 영상 = 우리 영상 중 가장 긴 것):

| 단계 | 시간 |
|---|---|
| 720p 인코딩 | 5.99초 |
| 480p 인코딩 | 4.24초 |
| HLS 패키징 (2종) | 0.38초 |
| 썸네일 | 0.09초 |
| **합계** | **약 10.5초** (영상 길이의 0.1배속) |

중앙값 21.5초 영상이면 **4초 내외**다. AI 합성 자체가 이보다 훨씬 비싸다.

> **배치로 미루면 안 되는 이유**: 갓 올라온 영상에 화질 사다리가 없다.
> 숏폼 피드는 최신 영상을 우선 노출하므로, **사다리가 가장 필요한 영상이 비게 된다.**

### 6.2 인코딩 파라미터 — 그냥 값이 아니라 전제조건이다

```bash
# 렌디션 (720p 예시, 30fps 기준)
ffmpeg -i in.mp4 -vf "scale=-2:720,fps=30" \
  -c:v libx264 -preset veryfast -crf 26 \
  -maxrate 1200k -bufsize 2400k \
  -g 60 -keyint_min 60 -sc_threshold 0 \
  -c:a aac -b:a 96k -movflags +faststart out.mp4
```

| 옵션 | 왜 필요한가 |
|---|---|
| `-g 60 -keyint_min 60 -sc_threshold 0` | **2초마다 강제 키프레임.** 조각 경계는 키프레임에만 놓인다. 화질 간 키프레임 시각이 다르면 **전환 자체가 불가능하다** |
| `-maxrate` / `-bufsize` | **비트레이트 상한.** CRF 만 쓰면 내용에 따라 원본 대비 15~69% 로 **4.6배 편차**가 난다. ABR 은 재생목록의 `BANDWIDTH` 값으로 화질을 고르므로 사다리가 예측 가능해야 한다 |
| `-movflags +faststart` | moov 를 앞으로. 원본은 이미 충족이나 산출물에도 유지 |
| `scale=-2:720` | **세로 영상이라 짧은 변 기준.** 9:16 소스에서 406×720 이 된다 |

**검증 완료**: 이 파라미터로 인코딩한 720p·480p 의 키프레임이
양쪽 다 정확히 **0·2·4·6·8·10초**에 놓인다. `-maxrate 1200k` 를 건 720p 는
1.06Mbps 로 상한 안에 들어왔다.

### 6.3 HLS 패키징 — 파일이 폭증하지 않는다

```bash
ffmpeg -i 720p.mp4 -c copy \
  -f hls -hls_time 2 -hls_playlist_type vod \
  -hls_segment_type fmp4 -hls_flags single_file \
  -hls_fmp4_init_filename init.mp4 \
  -hls_segment_filename 720/data.m4s  720/index.m3u8
```

**재인코딩이 필요 없다**(`-c copy`). 0.19초면 끝난다.

산출물 (영상 1개, 화질 2종):

```
master.m3u8
480/index.m3u8   480/data.m4s
720/index.m3u8   720/data.m4s
                                → 총 5개
```

조각 31개가 전부 `data.m4s` **한 파일 안의 바이트 구간**으로 지정된다.

```
#EXT-X-MAP:URI="data.m4s",BYTERANGE="1452@0"
#EXTINF:2.000000,
#EXT-X-BYTERANGE:322186@1452
data.m4s
```

> 옛날 TS 조각 방식이면 영상 1개에 60개 이상이 된다. **바이트레인지 방식이라
> 파일 폭증이 없다** — 이게 ABR 도입 비용을 낮추는 핵심이다.

마스터 재생목록:

```
#EXTM3U
#EXT-X-VERSION:7
#EXT-X-STREAM-INF:BANDWIDTH=593831,RESOLUTION=270x480
480/index.m3u8
#EXT-X-STREAM-INF:BANDWIDTH=1064058,RESOLUTION=406x720
720/index.m3u8
```

### 6.4 썸네일 추출

```bash
ffmpeg -ss 1.5 -i in.mp4 -frames:v 1 -vf scale=-2:1280 -q:v 5 thumb.jpg
```

| 항목 | 값 | 이유 |
|---|---|---|
| 추출 지점 | **1.5초** | **첫 프레임이 아니다.** 페이드인·모션블러·인물 프레임 밖인 경우가 많다 |
| 해상도 | 720×1280 | 원본 해상도로 뽑으면 120KB. 피드에선 과하다 |
| 용량 목표 | 20~40KB | 30개 목록이면 0.9MB vs 3.6MB 차이 |

`thumbnail_key` 는 이미 **NOT NULL** 이라 워커가 어차피 만들어야 한다.

### 6.5 URL 원칙

| 대상 | 방식 |
|---|---|
| 공개 영상 | CloudFront 일반 URL |
| **비공개 영상** | **CloudFront 서명 URL / 쿠키** |

**S3 presigned URL 을 쓰지 않는다.** 서명 쿼리스트링이 사용자·만료마다 달라지는데,
그 값이 캐시 키에 들어가면 **적중률이 0%** 가 되고, 캐시 키에서 빼면 서명이
무의미해진다. 어느 쪽도 성립하지 않는다.

CloudFront 서명은 엣지에서 검증하므로 캐시가 유지된다. 쿠키 방식은 피드처럼
여러 파일을 연속으로 받는 화면에 특히 맞는다.

### 6.6 API 영향

- **`videoUrl` 이 단일 MP4 에서 HLS 재생목록(`master.m3u8`) 주소로 바뀐다** —
  명세서 §8.2 등 참여 영상 응답 항목
- `thumbnailUrl` 은 변경 없음 (이미 존재)
