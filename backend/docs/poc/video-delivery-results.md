## 1. 용어

| 용어 | 뜻 |
|---|---|
| **N** | 프리페치 개수 — 다음 **몇 개** 영상을 미리 받을까 |
| **T** | 프리페치 길이 — 각각 **앞 몇 초**만 받을까 |
| **TTFF** | Time To First Frame. 스와이프하고 **첫 그림이 뜰 때까지** 걸리는 시간 |
| **스톨** | 재생 **도중** 멈추는 것 (버퍼링). TTFF 와 달리 여러 번 발생한다 |
| **moov** | MP4 안의 목차(색인). 플레이어가 이걸 먼저 읽어야 재생을 시작한다. 파일 **앞**에 있어야 왕복이 한 번 덜 든다 |
| **렌디션** | 같은 영상의 다른 화질 사본 |
| **egress** | 서버에서 나가는 트래픽 = CDN 요금이 붙는 대상 |

`N=2, T=1.5` = "다음 2개 영상의 앞 1.5초씩을 미리 받아둔다"

## 2. 테스트 환경

### 2.1 구성

```
┌─────────────────┐         ┌──────────────────┐
│  poc-harness    │  HTTP   │   poc-origin     │
│                 │ ──────► │                  │
│  ffmpeg/ffprobe │  Range  │  nginx           │
│  curl           │         │  /videos/     ◄── VIDEO_DIR (호스트, 읽기전용)
│  python3        │         │  /renditions/ ◄── 720p·480p 사본
│                 │         │                  │
│  = 가짜 앱      │         │  access.csv ────► 서버 측 바이트 진실
└─────────────────┘         └──────────────────┘
                                     ▲
                              tc netem — 네트워크 흉내
```

본 인프라(`local-infra/docker-compose.yml`)와 분리했다. PoC 는 PG·MQ 가 필요 없고,
측정 중 다른 컨테이너가 같은 네트워크에서 트래픽을 내면 수치가 오염된다.

### 2.2 왜 안드로이드 없이 되나

```
첫 화면 = [네트워크로 받는 시간] + [폰이 디코딩하는 시간]
            ↑ 전략이 바꾸는 항          ↑ 어느 전략이든 동일
```

디코딩 시간은 전략과 무관하게 같으므로 **순위는 네트워크 항에서만 갈린다.**
그 항은 ffmpeg + `tc netem` 으로 재현된다. 안드로이드는 확정된 결과만 구현하면 되고,
이 PoC 를 위한 별도 화면·계측을 만들 필요가 없다.

### 2.3 네트워크 흉내 — 무엇을 어떻게 조이나

실제 LTE 망이 아니다. 리눅스 커널의 `tc netem` 으로 **지연(RTT)과 대역폭** 두 가지만 조인다.

| 프로파일 | RTT | 대역폭 | 용도 |
|---|---|---|---|
| `wifi` | 10ms | 100Mbps | 기준선 |
| `lte_good` | 50ms | 20Mbps | **확정 타깃** |
| `lte_poor` | 100ms | 4Mbps | ABR 판정용 (스윕 기본값에 추가) |
| `3g` | 300ms | 1.5Mbps | netem 자체검사 전용 (스윕에 안 씀 — 세션 하나에 10분 초과) |

**진짜 걸리는지 검증** — 같은 영상의 앞 1MiB 를 프로파일만 바꿔 받았다:

| 프로파일 | 실측 | 이론값 | |
|---|---|---|---|
| off | 0.045s | — | 셰이핑 없음 |
| wifi | 0.174s | 0.10s + RTT | ✓ |
| lte_good | 0.703s | 8.39Mbit ÷ 20Mbps = 0.42s + RTT·슬로스타트 | ✓ |
| lte_poor | 2.568s | ÷ 4Mbps = 2.10s + 오버헤드 | ✓ |
| **3g** | **6.878s** | ÷ 1.5Mbps = 5.59 + 연결 0.3 + 첫바이트 0.3 + 램프 ≈ 6.8s | ✓ |

3g 6.878초가 핵심이다. 티켓 541 이 Windows 에서 남긴 기준선이 **6.833초** — 다른 OS·다른
셰이핑 방식인데 0.045초 차이로 재현됐다. `selfcheck.sh` 가 매 실행마다 이 검사를 자동으로 한다.

### 2.4 셰이핑 지점 — 환경에 따라 다르다

| 커널 | 거는 곳 | 비고 |
|---|---|---|
| ifb 있음 (리눅스) | **하네스 ingress** | 원칙. CloudFront 처럼 남의 서버도 조일 수 있다 |
| ifb 없음 (Docker Desktop macOS) | **origin egress** | origin 이 내보내는 방향이 곧 다운로드 경로다. 로컬 origin 만 가능 |

macOS 의 LinuxKit 6.10 커널에는 `ifb` 모듈이 없다(`modprobe: Module ifb not found`).
`run-all.sh`·`selfcheck.sh` 가 자동 판별한다.

> ⚠️ **받는 쪽에서 egress 를 걸면 안 된다.** 요청·ACK 만 조여지고 다운로드는 그대로 빨라서,
> **안 조여진 수치가 "측정 성공"으로 나온다.** `netem.sh` 는 ifb 가 없을 때 자동으로 egress 로
> 강등하지 않고 실패한다 — 호출자가 명시해야 한다.

### 2.5 한계 — 이 수치를 어디까지 믿을 수 있나

재현하는 것은 **고정 대역폭 + 고정 지연**뿐이다. 실제 셀룰러에 있는 것들은 없다:

- 지터 (지연 요동)
- 패킷 손실·재전송
- 기지국 핸드오버, 시간대별 혼잡
- 상·하향 비대칭

따라서 **"실제 LTE 에서 정확히 344ms 걸린다"가 아니라 "같은 조건에서 원본이 720p 보다 느리고,
4Mbps 에서 원본만 끊긴다"** 가 이 측정의 결론이다. 전략 간 **순위 비교**에는 유효하고,
절대값 예측에는 쓰면 안 된다.

`lte_good = 20Mbps·50ms` 라는 값 자체도 팀이 정한 가정이지 실측이 아니다.

### 4.1 영상 인벤토리 (실측)

| 태그 | 개수 | 용량 | 평균 비트레이트 | 범위 | moov 뒤 |
|---|---|---|---|---|---|
| `origin` (원본) | 31 | 279MB | **3.35Mbps** | 0.59~5.88 | **0/31** |
| `720p` (렌디션) | 31 | 84MB | 0.78Mbps | 0.27~1.18 | 0/31 |

**원본은 건드리지 않는다.**

### 4.2 측정 조합

- 네트워크 3종 × 화질 3종 × 정책 3종(`N=1,T=1.0` / `N=2,T=1.5` / `N=3,T=3.0`) × 세션 2 = 54 세션

## 5. 결과

### 5.1 계측 검증 — 통과

| 항목 | 결과 |
|---|---|
| 실행 수 | 60 |
| 시뮬레이터 합계 vs nginx 로그 합계 | **최대 오차 0.00%** (기준 ±5%) |

실행마다 요청 URL 에 `?s=<runid>` 를 붙여 서버 로그에서 갈라냈다. 정적 서빙은 쿼리스트링을
무시하므로 응답에는 영향이 없다. **이 검사가 통과해야 아래 수치가 의미를 갖는다.**

### 5.0 수치 정정 — 시뮬레이터 모델 결함

초판 수치에는 두 가지 결함이 있었다. 재버퍼 관련 수치를 전부 다시 측정했다.

1. **읽기앞서기 버퍼가 없었다.** "1초 재생하려고 1초치를 그때 받는" 모델이라
   실제보다 훨씬 잘 끊겼다. 실제 플레이어는 여유가 있을 때 앞질러 받아 버퍼로
   네트워크 요동을 흡수한다(ExoPlayer `DefaultLoadControl` 기본 최대 50초).
   30초 목표로 넣었다.
2. **화질 전환 시 앞부분을 다시 받았다.** ABR 의 데이터 사용량이 부풀어 보였다.

지표도 바꿨다 — **"멈춘 조각 수" → "멈춘 횟수 / 누적 초"**. 조각 수는 루프 구조에
좌우돼 모델을 바꾸면 비교가 성립하지 않는다.

| 예: 1.5Mbps / 720p | 초판 | **정정** |
|---|---|---|
| | 31회 | **3회 / 6초** |

### 5.2 재버퍼 — ABR 판정 (가장 중요)

한 세션(14개 시청, 144초 분량, 실시간 재생 모드) 동안 멈춘 횟수 / 누적 초:

| 네트워크 | origin (3.35Mbps) | 720p (0.78Mbps) | 480p (0.47Mbps) | **ABR** |
|---|---|---|---|---|
| `lte_good` 20Mbps | 0회 | 0회 | 0회 | 0회 |
| `lte_poor` 4Mbps | 5회 / 6초 | **0회** | 0회 | **0회** (전환 4회) |
| `3g` 1.5Mbps | 10회 / **170초** | 3회 / 6초 | 1회 / 0초 | **1회 / 0초** (전환 0회) |

**읽는 법**

- **원본 그대로는 안 된다.** 1.5Mbps 에서 누적 170초 멈춘다 — 재생 시간(144초)보다
  길다. 31개 중 4개가 5.88Mbps 라 물리적으로 재생이 불가능하다
- **4Mbps 는 720p 로 해결된다** (0회)
- 1.5Mbps 에서 720p 는 6초, 480p 는 0초. **차이가 크지 않다**
- **ABR 은 1.5Mbps 에서 480p 와 동일하게 동작한다**(전환 0회 — 올릴 여유가 없다고
  정확히 판단). 4Mbps 에서는 720p 로 올려 쓴다

### 5.2b 재생 중 대역폭 붕괴 — ABR 채택의 직접 근거

40초 재생 후 20Mbps → 1.5Mbps 로 떨어뜨린 시나리오(`--pace` 로 벽시계를 재생
시간에 맞춰 붕괴가 재생 중에 걸리게 했다):

| | egress | 멈춤 |
|---|---|---|
| 480p 고정 | 10.1MB | 0회 |
| 720p 고정 | 17.1MB | 2회 / 5초 |
| **ABR** | **11.0MB** | **0회** (전환 2회) |

- ABR 은 붕괴 전 720p, 붕괴 후 480p — **화질과 안정성을 모두 취하고 egress 는
  720p 고정의 64%**
- 480p 고정도 멈춤 0 이지만 붕괴 전 20Mbps 구간의 화질을 통째로 포기한 대가다
- **영상 단위 URL 선택으로는 커버할 수 없다** — 이미 영상을 열고 재생 중이다

**노출 빈도**: 한 세션에서 10초 이상 시청한 영상은 14개 중 4개뿐이지만
**시청 시간의 75%** 를 차지한다. 붕괴가 임의 시점에 온다면 대부분 "긴 영상
재생 중"에 온다.

> 실시간 모드의 프리페치는 재생 중이 아니라 재생 후에 돈다(단일 스레드).
> 실제보다 낙관적이다.

### 5.3 TTFF

`TTFF(net)` = 측정값에서 도구 상수(ffmpeg 프로세스 시작·디코더 초기화, 31~49ms)를 뺀 값.

| 네트워크 | origin | 720p | 480p |
|---|---|---|---|
| `wifi` | 67ms | 56ms | 58ms |
| `lte_good` | **344ms** | **289ms** | **290ms** |
| `lte_poor` | 1041ms | 760ms | 696ms |

**두 가지가 나온다:**

1. **문서 목표 p50 < 200ms 가 LTE 양호에서 미달**이다. Wi-Fi 만 통과한다.
2. **화질을 낮춰도 거의 개선되지 않는다** (344 → 289ms, 16%). 첫 프레임에 필요한 바이트가 작아
   RTT 가 지배하기 때문이다. → **TTFF 개선은 ABR 로는 안 된다. 프리페치가 담당한다.**

> 설계문서는 TTFF(net)을 "ffmpeg 실행 시간"으로 정의해 도구 상수를 포함한 값에 200ms 목표를
> 걸었다. 상수를 빼고도 미달이므로 목표 자체를 재검토해야 한다.

### 5.4 프리페치 정책 — 이득 측정 방법을 찾았다

**바이트 쪽** (비실시간 스윕, origin):

| 정책 | 세션당 egress | 낭비율 |
|---|---|---|
| `N=1, T=1.0` | 34.6MB | 0.8~1.1% |
| `N=2, T=1.5` | 35.1MB | 2.1~2.5% |
| `N=3, T=3.0` | 36.8MB | 6.5~6.9% |
| `N=2, T=전체` | 1.8배 (480p 기준 10.1 → 18.0MB) | **12배** |

낭비율은 전체 프리페치를 빼면 목표(<30%)를 크게 밑돈다.

**이득 쪽** — TTFF 로는 안 잡힌다. TTFF 는 콜드 상태에서 파일을 처음 여는 시간이라
프리페치 유무와 무관하고, 실제로 정책이 바뀌어도 값이 변하지 않는다.

**실시간 모드의 멈춤으로 잡힌다.** 1.5Mbps / 720p:

| 정책 | egress | 낭비율 | 멈춤 |
|---|---|---|---|
| 없음 | 16.9MB | 0% | 6회 / 10초 |
| **N=2 × 1.5초** | 17.1MB | 1.5% | **3회 / 6초** |
| N=3 × 1.0초 | 17.1MB | 1.5% | 3회 / 7초 |
| N=2 전체 | 30.0MB | 10.6% | 1회 / 1초 |

`N=2×1.5s` 와 `N=3×1.0s` 는 받는 총량이 같고(3초 분량) 결과도 사실상 같다.
`N=2 전체`가 멈춤은 최소지만 egress 1.8배·낭비 7배를 쓰고, 그 이득은 ABR 과
중복된다.

**프리페치는 TTFF 장치가 아니라 재버퍼 방지 장치다.** 대역폭이 빠듯할수록 효과가 크고,
여유가 있으면(720p@4Mbps, 480p@1.5Mbps) 효과가 정확히 0 이다.

**→ 채택: `N=2, T=1.5초`** ([ADR-0010](../adr/0010-video-delivery.md) D3).
효과 차이가 작으므로 출시 후 클라이언트 계측으로 재조정하는 것을 전제로 한다.

### 5.5 트래픽 — 비용 추정용

**시청 아이템 1개당 egress** (14개 시청 세션 기준, `N=2,T=1.5`):

| 화질 | 아이템당 | 14개 세션 | 720p 대비 |
|---|---|---|---|
| origin | 4.04MB | 56.6MB | 3.3배 |
| **720p** | **1.22MB** | **17.1MB** | 1배 |
| 480p | 0.72MB | 10.1MB | 0.6배 |

**720p 렌디션으로 서빙하면 egress 가 원본 대비 1/3.3 로 준다.** CDN 요금에 직결된다.

설계문서 트래픽 모델식 대비 오차:

| 정책 | 오차 | 판정 |
|---|---|---|
| `N=1, T=1.0` | -5.8 ~ -7.4% | OK |
| `N=2, T=1.5` | -15.7 ~ -19.6% | OK (경계) |
| `N=3, T=3.0` | -34.6 ~ -41.2% | **±20% 초과** |

**식이 프리페치분을 이중계산한다.** 식은 프리페치 바이트를 시청 바이트 위에 그대로 더하는데,
실제로는 시청까지 이어진 아이템의 프리페치분이 시청 바이트에 이미 포함돼 있다(받아둔 구간을
다시 받지 않으므로). T 가 클수록 오차가 커지는 것이 그 증거다. 비용 산정에 쓰기 전에 고쳐야 한다.

## 8. CloudFront — 준비 완료, 측정 대기

### 배포 상태

| 항목 | 값 |
|---|---|
| 버킷 | `s3://motif-media/poc/` (ap-northeast-2) |
| 도메인 | `d21so2cpi8si9r.cloudfront.net` |
| 업로드 | `poc/videos/` 31개 279MB · `poc/renditions/720p/` 84MB · `poc/renditions/480p/` 51MB |
| 정리 | `aws s3 rm s3://motif-media/poc/ --recursive` |

`motif-media` 는 PoC 전용이 아니라 서비스 미디어 버킷이다(`assets/`·`profiles/`·`raw/` …).
그래서 PoC 파일은 전부 `poc/` 프리픽스 아래로 격리했다.

### 런북 §3 검증 — 통과

| 확인 | 결과 |
|---|---|
| Range | ✅ `HTTP/2 206` + `content-range: bytes 0-1023/7838799` |
| 캐시 2회차 | ✅ `Hit from cloudfront` |
| 쿼리스트링 캐시키 제외 | ✅ `?a=1`·`?a=2` 둘 다 Hit |
| HTTP/2 | ✅ |
| HTTP/3 | 미확인 |

쿼리스트링 제외 확인이 중요하다. 캐시 키에 들어갔으면 사용자마다 다른 객체가 되어
**적중률이 0%** 가 된다. 우리 시뮬레이터가 로그 구분용으로 붙이는 `?s=<runid>` 도
캐시를 깨지 않는다는 뜻이다.

> ⚠️ **런북 §3 의 `curl -sI -r 0-1023` 은 틀린 테스트다.** HEAD 는 본문이 없어
> CloudFront·S3 가 Range 를 무시하고 200 을 낸다 — 정상 배포에서도 실패로 보인다.
> GET 으로 바꿔야 한다: `curl -s -r 0-1023 -o /dev/null -D -`.
> `develop/infra` 의 런북도 같이 고쳐야 한다.

### 남은 측정

```bash
# --origin 만 바꾸면 된다. 도구 변경 없음
--origin https://d21so2cpi8si9r.cloudfront.net/poc/videos
--origin https://d21so2cpi8si9r.cloudfront.net/poc/renditions/720p
```

- 상위 2~3 조합 × 프로파일별 3회 (ADR 티켓 범위)
- CloudFront 표준 로그를 켜야 egress 대조(±5%)가 성립한다 — 런북 §4
- ⚠️ macOS 에서는 CloudFront 를 셰이핑할 수 없다(ifb 부재 → origin egress 방식인데 원격
  origin 은 못 조인다). 프로파일별 비교가 필요하면 **리눅스 호스트**에서 돌려야 한다
- ⚠️ 비용: 개인 프리티어 계정. 예산 알람(월 $5, 실제 85%/예측 100%) 설정 완료
