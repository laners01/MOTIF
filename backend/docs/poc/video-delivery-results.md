## 1. 용어

| 용어 | 뜻 |
|---|---|
| **N** | 프리페치 개수 — 다음 **몇 개** 영상을 미리 받을까 |
| **T** | 프리페치 길이 — 각각 **앞 몇 초**만 받을까 |
| **TTFF** | Time To First Frame. 스와이프하고 **첫 그림이 뜰 때까지** 걸리는 시간 |
| **스톨** | 재생 **도중** 멈추는 것 (버퍼링). TTFF 와 달리 여러 번 발생한다 |
| **moov** | MP4 안의 목차(색인). 플레이어가 이걸 먼저 읽어야 재생을 시작한다. 파일 **앞**에 있어야 왕복이 한 번 덜 든다 |
| **렌디션** | 같은 영상의 다른 화질 사본 |
| **egress** | 서버에서 나가는 트래픽 = CDN 요금이 붙는 대상 |

`N=2, T=1.5` = "다음 2개 영상의 앞 1.5초씩을 미리 받아둔다"

## 2. 테스트 환경

### 2.1 구성

```
┌─────────────────┐         ┌──────────────────┐
│  poc-harness    │  HTTP   │   poc-origin     │
│                 │ ──────► │                  │
│  ffmpeg/ffprobe │  Range  │  nginx           │
│  curl           │         │  /videos/     ◄── VIDEO_DIR (호스트, 읽기전용)
│  python3        │         │  /renditions/ ◄── 720p·480p 사본
│                 │         │                  │
│  = 가짜 앱      │         │  access.csv ────► 서버 측 바이트 진실
└─────────────────┘         └──────────────────┘
                                     ▲
                              tc netem — 네트워크 흉내
```

본 인프라(`local-infra/docker-compose.yml`)와 분리했다. PoC 는 PG·MQ 가 필요 없고,
측정 중 다른 컨테이너가 같은 네트워크에서 트래픽을 내면 수치가 오염된다.

### 2.2 왜 안드로이드 없이 되나

```
첫 화면 = [네트워크로 받는 시간] + [폰이 디코딩하는 시간]
            ↑ 전략이 바꾸는 항          ↑ 어느 전략이든 동일
```

디코딩 시간은 전략과 무관하게 같으므로 **순위는 네트워크 항에서만 갈린다.**
그 항은 ffmpeg + `tc netem` 으로 재현된다. 안드로이드는 확정된 결과만 구현하면 되고,
이 PoC 를 위한 별도 화면·계측을 만들 필요가 없다.

### 2.3 네트워크 흉내 — 무엇을 어떻게 조이나

실제 LTE 망이 아니다. 리눅스 커널의 `tc netem` 으로 **지연(RTT)과 대역폭** 두 가지만 조인다.

| 프로파일 | RTT | 대역폭 | 용도 |
|---|---|---|---|
| `wifi` | 10ms | 100Mbps | 기준선 |
| `lte_good` | 50ms | 20Mbps | **확정 타깃** |
| `lte_poor` | 100ms | 4Mbps | ABR 판정용 (스윕 기본값에 추가) |
| `3g` | 300ms | 1.5Mbps | netem 자체검사 전용 (스윕에 안 씀 — 세션 하나에 10분 초과) |

**진짜 걸리는지 검증** — 같은 영상의 앞 1MiB 를 프로파일만 바꿔 받았다:

| 프로파일 | 실측 | 이론값 | |
|---|---|---|---|
| off | 0.045s | — | 셰이핑 없음 |
| wifi | 0.174s | 0.10s + RTT | ✓ |
| lte_good | 0.703s | 8.39Mbit ÷ 20Mbps = 0.42s + RTT·슬로스타트 | ✓ |
| lte_poor | 2.568s | ÷ 4Mbps = 2.10s + 오버헤드 | ✓ |
| **3g** | **6.878s** | ÷ 1.5Mbps = 5.59 + 연결 0.3 + 첫바이트 0.3 + 램프 ≈ 6.8s | ✓ |

3g 6.878초가 핵심이다. 티켓 541 이 Windows 에서 남긴 기준선이 **6.833초** — 다른 OS·다른
셰이핑 방식인데 0.045초 차이로 재현됐다. `selfcheck.sh` 가 매 실행마다 이 검사를 자동으로 한다.

### 2.4 셰이핑 지점 — 환경에 따라 다르다

| 커널 | 거는 곳 | 비고 |
|---|---|---|
| ifb 있음 (리눅스) | **하네스 ingress** | 원칙. CloudFront 처럼 남의 서버도 조일 수 있다 |
| ifb 없음 (Docker Desktop macOS) | **origin egress** | origin 이 내보내는 방향이 곧 다운로드 경로다. 로컬 origin 만 가능 |

macOS 의 LinuxKit 6.10 커널에는 `ifb` 모듈이 없다(`modprobe: Module ifb not found`).
`run-all.sh`·`selfcheck.sh` 가 자동 판별한다.

> ⚠️ **받는 쪽에서 egress 를 걸면 안 된다.** 요청·ACK 만 조여지고 다운로드는 그대로 빨라서,
> **안 조여진 수치가 "측정 성공"으로 나온다.** `netem.sh` 는 ifb 가 없을 때 자동으로 egress 로
> 강등하지 않고 실패한다 — 호출자가 명시해야 한다.

### 2.5 한계 — 이 수치를 어디까지 믿을 수 있나

재현하는 것은 **고정 대역폭 + 고정 지연**뿐이다. 실제 셀룰러에 있는 것들은 없다:

- 지터 (지연 요동)
- 패킷 손실·재전송
- 기지국 핸드오버, 시간대별 혼잡
- 상·하향 비대칭

따라서 **"실제 LTE 에서 정확히 344ms 걸린다"가 아니라 "같은 조건에서 원본이 720p 보다 느리고,
4Mbps 에서 원본만 끊긴다"** 가 이 측정의 결론이다. 전략 간 **순위 비교**에는 유효하고,
절대값 예측에는 쓰면 안 된다.

`lte_good = 20Mbps·50ms` 라는 값 자체도 팀이 정한 가정이지 실측이 아니다.

## 4. 무엇을 어떻게 쟀나

### 4.1 영상 인벤토리 (실측)

| 태그 | 개수 | 용량 | 평균 비트레이트 | 범위 | moov 뒤 |
|---|---|---|---|---|---|
| `origin` (원본) | 31 | 279MB | **3.35Mbps** | 0.59~5.88 | **0/31** |
| `720p` (렌디션) | 31 | 84MB | 0.78Mbps | 0.27~1.18 | 0/31 |
| `480p` (렌디션) | 31 | 51MB | 0.47Mbps | 0.20~0.69 | 0/31 |

원본 상세: 길이 8.3~59.7초(중앙값 21.5초, 15~60초 구간은 21/31개),
해상도 1080×1920 22개·720×1280 4개·576×1024 4개·1080×1918 1개, GOP 1.57~8.33초.

> **설계문서 가정과 다른 점**: 문서는 720p·2.5Mbps 를 예시로 썼는데 실제는
> **1080p 위주·평균 3.35Mbps** 다. 트래픽 모델 계수를 이 값으로 갱신해야 한다.

렌디션은 `transcode.sh --rendition <높이>` 로 만든 사본이다 (libx264, CRF 26).
**원본은 건드리지 않는다.**

### 4.2 측정 조합

- 네트워크 3종 × 화질 3종 × 정책 3종(`N=1,T=1.0` / `N=2,T=1.5` / `N=3,T=3.0`) × 세션 2 = 54 세션
- 추가로 `lte_good`·`lte_poor` 에서 재버퍼 실측(실시간 재생 모드) 3화질 = 6 세션
- 시청 모델(설계문서 확정): 3초 스킵 40% / 절반 30% / 완시청 30%
- **이탈 확률 0.05/스와이프** ← 제안값. 설계문서에 없다. §7 참조

## 5. 결과

### 5.1 계측 검증 — 통과

| 항목 | 결과 |
|---|---|
| 실행 수 | 60 |
| 시뮬레이터 합계 vs nginx 로그 합계 | **최대 오차 0.00%** (기준 ±5%) |

실행마다 요청 URL 에 `?s=<runid>` 를 붙여 서버 로그에서 갈라냈다. 정적 서빙은 쿼리스트링을
무시하므로 응답에는 영향이 없다. **이 검사가 통과해야 아래 수치가 의미를 갖는다.**

### 5.2 재버퍼 — ABR 판정 (가장 중요)

한 세션(14개 시청) 동안 재생이 멈춘 횟수:

| 네트워크 | origin (3.35Mbps) | 720p (0.78Mbps) | 480p (0.47Mbps) |
|---|---|---|---|
| `lte_good` 20Mbps | 0 | 0 | 0 |
| **`lte_poor` 4Mbps** | **60회** | **0** | **0** |

- 설계문서 목표 "LTE 양호까지 재버퍼 0" 은 **원본으로도 충족**한다
- 그러나 **4Mbps 환경에서 원본은 사실상 계속 끊긴다.** 5.88Mbps 짜리 영상 4개는 4Mbps 링크에서
  물리적으로 실시간 재생이 불가능하다(0.68배)
- **720p 렌디션이 이를 완전히 해소한다.** 480p 를 추가할 이유가 이 데이터엔 없다

> 재버퍼 시뮬레이션은 프리페치를 재생 **중**이 아니라 재생 **후**에 돌린다(스레드 미사용).
> 실제보다 낙관적이지만 판정은 안 바뀐다 — 원본은 이미 전 구간 스톨이고,
> 720p 는 여유가 5배(0.78 + 프리페치 0.17 vs 4Mbps)다.

### 5.3 TTFF

`TTFF(net)` = 측정값에서 도구 상수(ffmpeg 프로세스 시작·디코더 초기화, 31~49ms)를 뺀 값.

| 네트워크 | origin | 720p | 480p |
|---|---|---|---|
| `wifi` | 67ms | 56ms | 58ms |
| `lte_good` | **344ms** | **289ms** | **290ms** |
| `lte_poor` | 1041ms | 760ms | 696ms |

**두 가지가 나온다:**

1. **문서 목표 p50 < 200ms 가 LTE 양호에서 미달**이다. Wi-Fi 만 통과한다.
2. **화질을 낮춰도 거의 개선되지 않는다** (344 → 289ms, 16%). 첫 프레임에 필요한 바이트가 작아
   RTT 가 지배하기 때문이다. → **TTFF 개선은 ABR 로는 안 된다. 프리페치가 담당한다.**

> 설계문서는 TTFF(net)을 "ffmpeg 실행 시간"으로 정의해 도구 상수를 포함한 값에 200ms 목표를
> 걸었다. 상수를 빼고도 미달이므로 목표 자체를 재검토해야 한다.

### 5.4 프리페치 정책 — ⚠️ 결론을 낼 수 없다

| 정책 | 세션당 egress (origin) | 낭비율 | TTFF |
|---|---|---|---|
| `N=1, T=1.0` | 34.6MB | 0.8~1.1% | 344ms |
| `N=2, T=1.5` | 35.1MB | 2.1~2.5% | 344ms |
| `N=3, T=3.0` | 36.8MB | 6.5~6.9% | 344ms |

낭비율은 셋 다 목표(<30%)를 크게 밑돈다. 그런데 **TTFF 열이 정책에 따라 전혀 변하지 않는다.**

설계문서가 TTFF 를 "프로파일별"로만 정의했기 때문이다 — 콜드 상태에서 파일을 처음 여는 시간이라
프리페치 유무와 무관하다. 그래서 이 표는 **"N·T 를 키우면 낭비만 늘고 이득은 0"** 이라고 말하고,
`N=1` 이 자동으로 이긴다. **그건 사실이 아니라 이득을 재는 지표가 없어서다.**

시뮬레이터 구조에도 원인이 있다. 지금은 "현재 것 시청 → 다음 것 프리페치"를 시간 축 없이 순차로
돈다. N 을 키우는 이득은 사용자가 **3초씩 연속으로 빠르게 스킵할 때**(시청 모델의 40%) 나타나는데,
그 상황이 재현되지 않는다.

**→ N·T 결론은 보류.** 필요한 것: 실시간 모드에서 연속 스킵 시나리오 + 스와이프 순간의
확보 버퍼(초)를 아이템별로 기록. 티켓 5 범위이거나 지표 정의 개정 사항이다.

### 5.5 트래픽 — 비용 추정용

**시청 아이템 1개당 egress** (14개 시청 세션 기준, `N=2,T=1.5`):

| 화질 | 아이템당 | 14개 세션 | 720p 대비 |
|---|---|---|---|
| origin | 4.04MB | 56.6MB | 3.3배 |
| **720p** | **1.22MB** | **17.1MB** | 1배 |
| 480p | 0.72MB | 10.1MB | 0.6배 |

**720p 렌디션으로 서빙하면 egress 가 원본 대비 1/3.3 로 준다.** CDN 요금에 직결된다.

설계문서 트래픽 모델식 대비 오차:

| 정책 | 오차 | 판정 |
|---|---|---|
| `N=1, T=1.0` | -5.8 ~ -7.4% | OK |
| `N=2, T=1.5` | -15.7 ~ -19.6% | OK (경계) |
| `N=3, T=3.0` | -34.6 ~ -41.2% | **±20% 초과** |

**식이 프리페치분을 이중계산한다.** 식은 프리페치 바이트를 시청 바이트 위에 그대로 더하는데,
실제로는 시청까지 이어진 아이템의 프리페치분이 시청 바이트에 이미 포함돼 있다(받아둔 구간을
다시 받지 않으므로). T 가 클수록 오차가 커지는 것이 그 증거다. 비용 산정에 쓰기 전에 고쳐야 한다.

## 7. 팀 확정이 필요한 값

| # | 항목 | 현재 | 왜 정해야 하나 |
|---|---|---|---|
| 1 | **이탈 확률** | 0.05/스와이프 (제안값) | 설계문서 시청 모델에 이탈이 없다. 이탈이 없으면 피드를 끝까지 소비해 **프리페치 낭비가 구조적으로 0** 이 되고, N·T 를 키울수록 유리하기만 해서 최적값이 N=∞ 로 나온다 |
| 2 | **`lte_poor` 를 정식 프로파일로** | 스윕 기본값에 추가함 | 확정 2종(wifi·lte_good)은 여유가 8배 이상이라 **재버퍼가 나올 수 없다** — ABR 판정 게이트가 열리지 않는다. 실제로 lte_poor 에서만 문제가 드러났다 |
| 3 | **TTFF 목표치** | p50<200ms 미달 | LTE 양호에서 289~344ms. 목표를 낮출지, 개선 방안을 찾을지 |
| 4 | **프리페치 이득 지표 신설** | 없음 | §5.4. 없으면 N·T 결론을 못 낸다 |
| 5 | **트래픽 모델식** | 이중계산 | §5.5 |

## 8. 다음 — CloudFront 대조

로컬 origin 결과는 위와 같고, 남은 것은 **실제 CDN 경로에서도 같은 결과가 나오는지**다.

- 런북: `infra/setup/video-poc-cdn.md` (티켓 542 — `develop/infra` 브랜치에 있다)
- 방법: 같은 하네스에서 `--origin` 만 CloudFront 도메인으로 바꾼다. 도구 변경 없음
- 추가로 확인할 것: 캐시 적중률(>90% 목표), 쿼리스트링이 캐시 키에서 빠졌는지
- ⚠️ 비용: 팀 인프라에 AWS 콘솔이 없어 **개인 프리티어 계정**을 쓴다. 측정 트래픽이 곧 개인 비용이라
  런북이 비용 알람을 1순위로 둔다
- ⚠️ macOS 에서는 CloudFront 를 조일 수 없다(ifb 부재). 셰이핑 없는 대조만 가능하고,
  프로파일별 비교가 필요하면 리눅스 호스트에서 돌려야 한다
