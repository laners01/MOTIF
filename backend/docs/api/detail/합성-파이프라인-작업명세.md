# 합성 파이프라인 — 작업 명세 (AI 서버 연동)

**개정 2026-09-22 (초판 09-18) · 짝 문서: [AI 서버 명세 v0.5](../MOTIF_AI서버_명세서_v0_5.md)**

AI 팀은 **GCP Cloud Run Jobs** 로 합성을 돈다. Cloud Run Job 은 상주하지 않아 큐를 구독할 수 없다 —
AI 와의 경계는 **HTTP 양방향**(우리가 접수 POST 1개, AI 가 콜백 POST 2개)이고, **우리 내부 큐는 그대로**다.
이 문서는 백엔드가 만들어야 할 것을 적는다. AI 팀에 건넨 계약은 AI 서버 명세이고, 어긋나면 그쪽을 먼저 고친다.

## 2. 설계 — 누가 무엇을 언제

원칙 넷.

1. **`composite_jobs` 를 쓰는 곳은 core-api 하나다.** AI 도 app-media 도 쓰지 않는다
2. **워커는 "했다" 만 보고한다.** DONE·FAILED 판정, `motif_results` 생성, FCM 은 core 가 한다
3. **FCM 은 core 가 확정한 뒤에만 나간다.** 앱은 폴링하지 않는다(§13.3) — 푸시가 먼저 가면 앱이 `PROCESSING` 을 본다
4. **AI 와는 HTTP 셋뿐이다.** 접수 1개(우리 → AI), 콜백 2개(AI → 우리). GCP 자격증명을 우리가 들지 않는다 — AI 팀의 접수 서비스가 Job 을 띄운다. 우리가 `jobs.run` 을 직접 부르는 안은 서비스 계정 키 관리와 OAuth 코드가 따라와서 버렸다

### 시퀀스

```
앱        core-api                 AI 접수 서비스     AI 합성 Job(GPU)    app-media        알림
│ 13.1     │                          │                 │                  │              │
│────────▶│ UPLOADED, presign        │                 │                  │              │
│ PUT raw  │                          │                 │                  │              │
│ 13.2     │                          │                 │                  │              │
│────────▶│ HEAD raw → QUEUED (커밋) │                 │                  │              │
│          │── POST {잡 JSON} ───────▶│ Job 실행        │                  │              │
│          │◀─ 202 ───────────────────│────────────────▶│ S3 GET ×2        │              │
│          │ PROCESSING               │                 │ 합성             │              │
│          │                          │                 │ S3 PUT results/  │              │
│          │◀── POST /done ─────────────────────────────│                  │              │
│          │── job.media ──────────────────────────────────────────────────▶│ HLS·썸네일  │
│          │                          │                 │                  │ S3 PUT private/│
│          │◀── composite.packaged ─────────────────────────────────────────│              │
│          │ DONE + 키 · MOTIF 는 motif_results                             │              │
│          │── composite.finished ──────────────────────────────────────────────────────▶│ FCM
│◀ FCM ────────────────────────────────────────────────────────────────────────────────────│
│ 13.3     │                          │                 │                  │              │
│────────▶│ 결과                     │                 │                  │              │
```

실패는 세 갈래다.

- AI 가 `/failed` → core `FAILED` + `fail_code` → `composite.finished(FAILED)` → FCM
- 접수가 실패(503·타임아웃) → 잡은 `QUEUED` 그대로 → **스윕**이 2분 뒤 재접수, 3회째면 `FAILED(STUCK)`
- Job 이 콜백 없이 죽음(task-timeout·OOM) 또는 app-media 실패(`dlq.job.media`) → `PROCESSING` 정체 → **스윕**이 `task-timeout + 5분` 뒤 `FAILED(STUCK)`

### 상태 전이

| 전이 | 누가 | 계기 |
|---|---|---|
| `UPLOADED` 생성 | core §13.1 | — |
| `UPLOADED → QUEUED` | core §13.2 / §13.4 | HEAD raw 통과. **여기서 커밋** |
| `QUEUED → PROCESSING` | core 접수 호출기 | 접수 **202**. 커밋 뒤(AFTER_COMMIT) 별도 트랜잭션 |
| `QUEUED` 유지 | core 접수 호출기 | 접수 실패. 스윕이 재접수 |
| `PROCESSING` 유지 + `job.media` 발행 | core 콜백 `/done` | `QUEUED` 에서 와도 받는다(202 응답이 유실된 경우) |
| `QUEUED\|PROCESSING → FAILED` | core 콜백 `/failed` · 스윕 | `fail_code` 기록 |
| `PROCESSING → DONE` | core evt.core | `composite.packaged` |
| `FAILED → QUEUED` | core §13.4 | 사용자 재시도 → 재접수 |

`PROCESSING` = **"AI 에 접수됐다"** (AI 실행 중이든 HLS 가공 중이든). 명세의 "워커 처리 중" 과 같은 뜻이다. 앱은 `QUEUED`·`PROCESSING` 을 같은 "진행 중" 으로 그린다.

### 내부 라우팅 키

`evt.core`·`evt.notification` 이 둘 다 `composite.*` 로 묶여 있다. 바인딩을 바꾸면 브로커 재기동이라 **바꾸지 않고 각 컨슈머가 자기 것만 처리하고 나머지는 ack 한다**.

| 키 | 발행 | 처리 | 무시(ack) |
|---|---|---|---|
| `composite.packaged` | app-media | core | 알림 |
| `composite.finished` | core | 알림 | core |

AI 관련 키(`composite.done|failed`)는 더 이상 흐르지 않는다. 큐 `job.composite` 와 계정 `gpu-worker` 는 남아 있어도 무해하다 — 정리는 3.3.

## 3. 계약

### 3.1 HTTP — core-api 소유 (`domain/composite/dto/`)

REST 는 camelCase 가 규약(§1.3)이지만 **AI 가 만지는 JSON 은 전부 snake_case** 로 통일한다 — Python 쪽에 표기법이 둘이면 반드시 한 번 틀린다. DTO 클래스에 `@JsonNaming(SnakeCaseStrategy)` 한 줄이다(Jackson 3 `tools.jackson.databind`). 응답 봉투는 그대로 camelCase 다 — AI 는 상태 코드만 본다.

| DTO | 방향 | 필드 |
|---|---|---|
| `CompositeJobPayload` | core → AI 접수 본문 | `jobUuid`, `jobType`, `attempt`, `rawVideoKey`, `baseVideoKey`, `outputVideoKey`, `correctionEnabled`, `participantMask`, `List<Slot> slots`, `baseDurationMs` — `Slot(participantMask, Anchor)`, `Anchor(x, y, r)`(썸네일 대비 비율, 옛 행은 `null`) |
| `WorkerDoneRequest` | AI → `/done` 본문 | `resultVideoKey`(필수), `processingMs`, `attempt`, `workerId` |
| `WorkerFailedRequest` | AI → `/failed` 본문 | `failCode`(필수, `^[A-Z_]{1,30}$`), `failMessage`(≤500), `processingMs`, `attempt`, `workerId` |

헤더: 토큰 `X-Motif-Worker-Token`(상수 `WorkerHeaders.TOKEN`), 추적 `X-Request-Id`(`RequestIdFilter.HEADER_NAME` 그대로).

JSON 예시는 AI 서버 명세 §3 이 원본이다. Swagger 는 클라이언트 계약이라 콜백 컨트롤러는 `@Hidden`.

### 3.2 MQ — `module-event` (additive-only)

| record | 변경 | 필드 |
|---|---|---|
| `CompositePackagedEvent` | **신규** (app-media → core) | `eventId`, `occurredAt`, `mediaJobUuid`, `sourceType`, `sourceSeq`, `outputPrefix`, `masterKey`, `thumbnailKey`, `durationMs` |
| `CompositeFinishedEvent` | **신규** (core → 알림) | `eventId`, `occurredAt`, `jobUuid`, `jobType`, `userSeq`, `status`(`DONE`\|`FAILED`), `failCode`, `resultSeq` |
| `RoutingKeys` | 추가 | `COMPOSITE_PACKAGED = "composite.packaged"`, `COMPOSITE_FINISHED = "composite.finished"` |

### 3.3 정리 대상 — 연동 뒤에, 지워도 남겨도 무해

`CompositeJobRequestedEvent`·`CompositeJobDoneEvent` · `DevJobService`·`DevJobEventRelay`·`DevJobController` · 알림 리스너의 `COMPOSITE_DONE` case · `RoutingKeys.JOB_COMPOSITE`·`COMPOSITE_DONE` · MQ 계정 `gpu-worker`(postStart) · 큐 `job.composite`(definitions — 재기동 필요, 급하지 않다). README "파이프라인 스모크" 절은 4.8 과 함께 고친다.

### 4.2 core-api — §13 API 4개 (`domain/composite/`)

상세 계약은 [`13-composite.md`](13-composite.md). 여기는 구현 메모만.

**공통**

- `CompositeJob` 에 정적 팩터리 + 전이 메서드 — `create(...)`, `queue()`, `markSubmitted()`(→PROCESSING), `complete(masterKey, thumbKey)`, `fail(code)`, `retry()`. 전이마다 현재 상태를 검사하고 어긋나면 던진다(CHECK 에 걸리기 전에 잡는다)
- `CompositeErrorCode` 신설: `JOB_NOT_FOUND`(404) · `RAW_NOT_UPLOADED`(409) · `JOB_NOT_REQUESTABLE`(409) · `JOB_NOT_RETRYABLE`(409) · `RAW_VIDEO_EXPIRED`(410). `ASSET_ACCESS_DENIED`(403) 는 `AssetErrorCode` 에 있는지 보고 없으면 거기 넣는다
- `MediaKeys` 에 셋 추가: `forRawUpload(jobUuid)` = `raw/{jobUuid}.mp4` · `forWorkerOutput(jobType, jobUuid)` = `results/{challenge|motif}/{jobUuid}.mp4` · `sourceMp4Of(key)` = `…/master.m3u8` 이면 `prefixOf(key) + ".mp4"`, 아니면 그대로
- 타인 잡은 전부 404 `JOB_NOT_FOUND`(존재 은닉)

**13.1 POST `/api/v1/composite-jobs`**

- CHALLENGE: 챌린지 비삭제 → `participantMask` 가 단일 비트면 `ChallengeParticipantRepository.findByChallengeSeqAndSlotOrder` 조회, 슬롯이 없거나 편집본(`editedChallengeKey`)이 없으면 404 `EDITED_CHALLENGE_NOT_FOUND`. 조합 마스크(비트 2개 이상)는 400 *(2026-09-21 — 조합 폐기)*
- MOTIF: `AssetQueryService.myAccess` 재사용 — `NONE` 이면 403 `ASSET_ACCESS_DENIED`. `PREMIUM` 은 `OWNED` 만 통과(§11 규칙)
- `raw_video_key = MediaKeys.forRawUpload(jobUuid)` 로 행 생성(`UPLOADED`) → `objectStore.presignPut(key, "video/mp4", …, 600s)`. 크기 상한은 `motif.admin.media.video.max-size` 재사용(기본안)
- 응답 201 `{ jobUuid, uploadUrl, expiresIn: 600 }`

**13.2 POST `/{jobUuid}/request`**

- `objectStore.exists(rawKey)` → 없으면 409 `RAW_NOT_UPLOADED`. 상태 `UPLOADED` 아니면 409 `JOB_NOT_REQUESTABLE`
- CHALLENGE 는 본문 `correctionEnabled` 저장, MOTIF 는 `false` 고정
- `queue()` → 내부 이벤트 `CompositeJobQueuedEvent(jobSeq)` → **커밋 후** 접수 호출기(아래) → 응답 202 `{ jobUuid, status }`. 접수가 실패해도 202 다 — 잡은 `QUEUED` 로 남고 스윕이 되살린다

**접수 호출기 `CompositeJobSubmitter`** (`@TransactionalEventListener(AFTER_COMMIT)`)

- 페이로드는 **잡 행에서 조립**한다 — 13.2·13.4·스윕이 같은 조립기(`CompositeJobPayloads.from(job, challenge, edited)` / `from(job, asset)`)를 쓴다
  - `baseVideoKey` = CHALLENGE 는 `sourceMp4Of(edited.edited_challenge_key)`, MOTIF 는 `sourceMp4Of(asset.video_key)`. **`video_key` 는 app-media 가 `master.m3u8` 로 바꿔 놓은 값**이라 그대로 보내면 AI 가 재생목록을 영상으로 연다(편집본은 통짜 MP4 라 되돌릴 것이 없다)
  - `slot` = 교체 대상 슬롯 **하나**, `anchor` 그대로(618 — bbox 없음. AI 에는 위치 힌트다). MOTIF 는 `null` 이다. **배열이 아니다** *(2026-09-22 — 구 `slots[]` + 바깥 `participant_mask`)*: 무교체가 폐기돼 CHALLENGE 는 언제나 슬롯 하나를 대체하고, 두 값은 그 하나에서 유도되던 흔적이었다
  - `outputVideoKey` = `MediaKeys.forWorkerOutput`
- `RestClient` 로 `POST {motif.composite.submit-url}`, 헤더 토큰 + `X-Request-Id`(MDC 값), 타임아웃 연결 3s / 읽기 15s
- **202** → `markSubmitted()` 를 **`REQUIRES_NEW` 트랜잭션**으로(AFTER_COMMIT 단계라 원 트랜잭션은 이미 끝났다). 그 외·예외 → WARN 로그만, 상태 유지
- 설정 `motif.composite.submit-url`·`worker-token`·`task-timeout`(스윕 기준값). prod 는 `AI_SUBMIT_URL`(configmap)·`MOTIF_WORKER_TOKEN`(secret), local 은 `http://localhost:18080/submit`·`motif-local-worker-token`

**13.3 GET `/{jobUuid}`**

- CHALLENGE: `DONE` 이면 `mediaUrlResolver.resolvePlaylist(resultVideoKey)` · `resolve(resultThumbnailKey)`. 그 외 `null`
- MOTIF: `DONE` 이면 `MotifResultRepository.findByJobSeq`(추가) → `resultSeq`
- 실패해도 200, `status`·`failCode` 로 판단(명세)

**13.4 POST `/{jobUuid}/retry`**

- `FAILED` 아니면 409 · `objectStore.exists(rawKey)` 실패면 410 `RAW_VIDEO_EXPIRED`
- `retry()` = `QUEUED`, `fail_code=null`, `attempt+1` → 같은 접수 경로. 응답 202 `{ jobUuid, status, attempt }`

### 4.3 core-api — 콜백 (`domain/composite/worker/`)

- **`WorkerSecurityConfig @Order(2)`** — `securityMatcher("/api/worker/**")`, 세션 없음, `WorkerTokenFilter` 하나. `SecurityConfig` 는 `@Order(3)` 으로 밀린다(catch-all 은 마지막이어야 한다 — `AdminSecurityConfig` 주석과 같은 이유)
- `WorkerTokenFilter`: 헤더 `X-Motif-Worker-Token` 을 설정값과 **`MessageDigest.isEqual`** 로 대조. 다르면 `SecurityErrorWriter` 로 401 봉투(`UNAUTHORIZED`). 토큰 설정이 비어 있으면 **전부 401**(fail-closed — `ADMIN_ALLOWED_CIDRS` 빈 값과 같은 태도)
- `WorkerCallbackController` (`@Hidden`)

| 엔드포인트 | 서비스 | 규칙 |
|---|---|---|
| `POST /api/worker/v1/composite-jobs/{jobUuid}/done` | `CompositeJobCompletionService.aiDone` | 잡 없으면 404. `DONE` 이면 200 무시. `QUEUED` 면 `markSubmitted()`(202 유실 복구). `processing_ms` 기록 → `mediaJobPublisher.publish(SOURCE_COMPOSITE_RESULT, jobSeq, resultVideoKey, MediaKeys.forCompositeResult(type, uuid), null)` → 200 |
| `POST …/{jobUuid}/failed` | `aiFailed` | 잡 없으면 404. `DONE` 이면 200 무시. `fail(failCode)` + `processing_ms` → `CompositeFinishedEvent(FAILED)` → 200 |

- 두 서비스 메서드는 `@Transactional` — `MediaJobPublisher`·`finished` 릴레이가 AFTER_COMMIT 이라 트랜잭션이 없으면 **아무 로그 없이 발행이 빠진다**
- `/done` 중복(AI 가 5xx 를 보고 재시도한 경우)은 `job.media` 를 한 번 더 낼 수 있다. app-media 가 `alreadyDone` 으로 거르고, 안 걸려도 같은 프리픽스에 같은 결과다 — 따로 막지 않는다. 문제가 보이면 Redis `SETNX composite:done:{jobUuid}`(ADR-0011) 한 줄
- 응답 시각은 `X-Request-Id` 가 AI 를 한 바퀴 돌아 온 값이다 — `RequestIdFilter` 가 승계하므로 로그가 이어진다

### 4.4 core-api — evt.core 컨슈머 (`domain/composite/CompositeEventListener`)

- 리스너 하나, `Message` + 라우팅 키 switch — `NotificationEventListener` 와 같은 모양
- 컨테이너 팩토리가 core-api 에 없다. `app-media/.../MqConfig` 의 `rabbitListenerContainerFactory` 를 그대로 — `defaultRequeueRejected=false`, 재시도 3회, `RejectAndDontRequeueRecoverer`
- `application-local-remote.yml` 에 `spring.rabbitmq.listener.simple.auto-startup: false`(ADR-0003, app-notification 과 같은 줄)
- 핸들러는 `@Transactional`(4.3 과 같은 이유)

| 키 | 처리 |
|---|---|
| `composite.packaged` | `sourceType != COMPOSITE_RESULT` 면 무시. 잡 조회(`sourceSeq`). `DONE` 이면 무시. CHALLENGE 면 `challenges.is_deleted` 재확인 → 삭제면 `fail("CHALLENGE_DELETED")`. 아니면 `complete(masterKey, thumbnailKey)`; MOTIF 면 `motif_results` INSERT `ON CONFLICT (job_seq) DO NOTHING`(`user_seq`·`asset_seq` 는 잡, `artist_seq` 는 에셋, `duration_ms` 는 이벤트 값·없으면 `asset.duration_ms`, `description NULL`) → `resultSeq` → `CompositeFinishedEvent(DONE, resultSeq)` |
| `composite.finished` | core 자신이 낸 것. ack 만 |
| 그 외 | 던져서 DLQ — 바인딩이 늘었을 때 조용히 사라지지 않게 |

- `MotifResult` 에 정적 팩터리 추가(지금은 생성자 없음)
- 멱등은 **상태 가드**로. `event_id` SETNX 는 두지 않는다

### 4.5 app-media — `COMPOSITE_RESULT` 분기

- `MediaJobProcessor.recordKeys` 의 `COMPOSITE_RESULT` UPDATE 를 **지운다**(CHECK 위반). 대신 `CompositePackagedEvent` 를 `motif.topic` / `composite.packaged` 로 발행. `durationMs` 는 `Ffmpeg` 에 `duration(Path)` 하나 더해 원본에서 잰다
- `alreadyDone` 의 `COMPOSITE_RESULT` 판정은 그대로 — core 가 같은 `master` 키를 쓰므로 `DONE` 이면 걸린다
- `RabbitTemplate` 은 Boot 자동구성이 `mqMessageConverter` 빈을 집어 쓴다. `x-request-id` 를 잇는 `setBeforePublishPostProcessors` 만 core-api `MqJacksonConfig` 에서 베낀다
- `CHALLENGE_ORIGIN`·`ASSET_PREVIEW` 는 건드리지 않는다
- **MQ 계정 `media` 쓰기 권한이 선행** → 4.9 #1

### 4.6 app-notification — `composite.finished`

- `NotificationEventListener` switch: `COMPOSITE_FINISHED` 처리, `COMPOSITE_PACKAGED` 는 debug 로그 + return. `default → throw` 는 그대로
- `PushMessage.compositeFinished(...)` — data-only, `type`: `COMPOSITE_DONE` | `COMPOSITE_FAILED`, `jobUuid`, `jobType`, `failCode`(실패만). 문구 기본안: 완료 "합성이 끝났어요" / CHALLENGE "결과를 확인하고 게시해 보세요" · MOTIF "보관함에 저장됐어요", 실패 "합성에 실패했어요" / 본문은 앱이 `failCode` 로 고른다
- 수신자 = `event.userSeq` 의 활성 기기 전부(`toOne` 재사용). 멱등 `claim/release` 그대로

### 4.7 core-api — 스윕 (`domain/composite/CompositeJobSweepJob`) — **연동 첫날 전에**

큐가 없어졌으니 **재전달을 해 주는 브로커도 없다.** 접수 실패와 콜백 없는 죽음을 되살리는 것이 전부 이 배치다.

- 등록은 `RankingConfig` 방식(`ScheduledTaskRegistrar`, 주기 설정값 `motif.composite.sweep-interval: 1m`). ShedLock 없음 — core-api 는 단일 레플리카
- `QUEUED` 이고 `COALESCE(mod_dttm, reg_dttm) < now() - 2분` → `attempt < 3` 이면 `attempt+1` 후 **재접수**(4.2 조립기·호출기 그대로), 아니면 `fail("STUCK")` + `finished(FAILED)`
- `PROCESSING` 이고 `< now() - (task-timeout + 5분)` → `fail("STUCK")` + `finished(FAILED)`. `task-timeout` 은 AI 팀이 준 값(설정 `motif.composite.task-timeout`, 기본 30m)
- 한 틱에 최대 20건. `ix_composite_jobs_stuck` 이 그 조회다
- 늦게 온 `/done`(스윕이 이미 `FAILED(STUCK)` 로 닫은 뒤)은 **받는다** — 결과는 실물이다. `FAILED → PROCESSING` 도 `markSubmitted` 계열로 허용하고, 실패 푸시 뒤에 완료 푸시가 한 번 더 가는 것은 감수한다

### 4.8 local-infra — HTTP 스텁

로컬에서 **운영과 같은 경로**(접수 → 콜백)가 돌아야 한다. 큐 스텁을 HTTP 스텁으로 바꾼다.

- `stub-worker/worker.py`: `POST /submit` → 202 `{execution: "stub-…"}` → 스레드에서 2초 뒤 `POST http://host.docker.internal:8081/api/worker/v1/composite-jobs/{job_uuid}/done` (`result_video_key = output_video_key`, 토큰 `motif-local-worker-token`, `X-Request-Id` 되돌림). `STUB_FAIL_CODE` env 가 있으면 `/failed` 로
- compose: 포트 `18080:8080`, Linux 용 `extra_hosts: ["host.docker.internal:host-gateway"]`, healthcheck 는 `GET /health`
- `application-local.yml`: `motif.composite.submit-url: http://localhost:18080/submit`, 토큰 더미
- README "파이프라인 스모크" 절: `POST /api/dev/jobs` 대신 13.1 → PUT → 13.2 로, 기대 로그를 "접수 202 → PROCESSING → 콜백 수신 → job.media 발행" 으로

## 7. 함정

1. **AFTER_COMMIT 릴레이는 트랜잭션이 없으면 침묵한다.** 콜백 서비스·evt.core 핸들러에 `@Transactional` 을 빼먹으면 `job.media`·`composite.finished` 가 나가지 않고 로그도 없다. `PROCESSING` 에서 멈춘 채 아무 흔적이 없으면 이것부터
2. **접수 호출은 커밋 뒤에.** 트랜잭션 안에서 부르면 AI 가 커밋 전에 콜백을 쳐서 404 를 받는다(빠른 실패 코드일 때 실제로 난다). AFTER_COMMIT 리스너에서 부르고, 상태 갱신은 `REQUIRES_NEW`
3. **`video_key` 는 MP4 가 아니다.** app-media 가 다녀간 챌린지·에셋의 `video_key` 는 `…/master.m3u8`. `sourceMp4Of` 로 되돌린다 — 안 하면 AI 가 재생목록 텍스트를 열려다 `RAW_UNREADABLE` 계열로 실패한다
4. **`result_*` 를 쓰는 유일한 순간은 `DONE` 전이와 같은 UPDATE 다.** 따로 쓰면 CHECK. app-media 가 그렇게 죽어 있었다
5. **알림 리스너에 새 키를 안 넣으면 DLQ 다.** 4.6 을 4.5 보다 먼저 배포한다
6. **`media` 권한 없이 app-media 가 발행하면 채널이 닫힌다**(`ACCESS_REFUSED`). 4.9 #1 이 4.5 배포보다 먼저다
7. **토큰 비교는 `MessageDigest.isEqual`.** `String.equals` 는 타이밍이 샌다. 토큰 미설정은 전부 401 — 조용히 열리는 쪽으로 기울지 않는다
8. **Cloud Run `--max-retries 0` 은 AI 팀 설정이다.** 기본값(3)이면 OOM 한 번에 같은 잡이 네 번 돈다. 체크리스트에 있지만 우리가 실행 목록으로 한 번 확인한다
9. **스윕 시간은 콜드스타트를 포함해야 한다.** `task-timeout + 5분` 보다 짧게 잡으면 정상 잡을 `STUCK` 으로 닫고 뒤늦은 `/done` 이 다시 살린다 — 푸시가 두 번 간다
10. **envFrom 은 파드 생성 시 한 번.** `MOTIF_WORKER_TOKEN`·`AI_SUBMIT_URL` 을 고쳤으면 `rollout restart`
