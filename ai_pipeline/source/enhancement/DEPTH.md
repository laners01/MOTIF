# run_depth.ipynb

현재 스케일·접지·박자 판정 수정 및 재실행 안내는 [PLACEMENT_REPAIR.md](PLACEMENT_REPAIR.md)를 참고하세요. 아래 이전 검토 기록은 보존합니다.

## 음악 구간 정렬

E-0에서 원본 FG/BG를 고른 뒤 E-0a를 실행합니다. 프로젝트의
`music_sync/core.py`에서 음악 특징 비교와 시작 시차 검출을 재사용합니다.
확실히 일치하는 공통 구간만 잘라 두 영상을 같은 프레임 수·길이로 맞춥니다.
같은 곡명이라도 다른 녹음·리믹스·배속·반복 구간에서는 정렬을 확정하지 못할 수 있습니다.
오디오가 없거나 판별 불가하면 이유를 표시하고 원본 입력을 사용합니다.

출력 기준은 원래 배경 FPS입니다. 전경도 이 FPS에 맞추며 영상 재생 속도를
바꾸지는 않습니다. 각 영상의 해상도는 유지하고 홀수 크기만 1픽셀 패딩합니다.
독립 앱의 30 FPS 고정·해상도 통일·Gradio UI는 가져오지 않았습니다.
프레임 격자에 맞춰 자르기 때문에 영상 시작점은 프레임 간격 수준의 오차가 있을 수 있습니다.
RGB 블러나 음원 분리 모델은 추가하지 않습니다.

정렬된 두 영상과 원본 경로·해시·시작점·일치 점수는
`output/music_sync/pair_*/sync.json`에 저장합니다. 동일 입력·코드는
`.cache/music_sync/`의 기록으로 재사용하며 원본 영상은 수정하지 않습니다.
E-1 이후 추적, SVOR, 자세/깊이 분석, 합성 및 최종 오디오는 모두
이 정렬된 구간을 사용합니다. 마지막 비교 셀의 양쪽에도 음악 정렬은 적용되며,
추가 춤 보정 전후를 비교합니다.

현재 커널의 이전 변수와 혼용하지 않도록 업데이트 후에는 첫 셀부터 실행합니다.
영상 선택을 바꾸면 E-0a부터 다시 실행합니다. 다른 노트북의 처리 흐름은 바꾸지 않았습니다.
추가 설치·모델 다운로드 없이 기존 video-layer의 NumPy/SciPy/OpenCV/FFmpeg를 사용합니다.

노트북의 진행 표시·모듈 갱신·입력 검사를 공통 함수로 정리하고, 사용하지 않는
그림자/조명 결과 변수와 이전 버전 안내를 제거했습니다. 원본 B를 복원하기 전
SVOR 결과를 그대로 다시 인코딩하던 E-2b의 중복 저장도 제거했습니다.
SVOR 3 step·65프레임 청크·16프레임 겹침, 춤 보정, 배치, 깊이 가림,
전경 선명도 유지 옵션과 자동 조명은 유지합니다.

CPU 검증에서는 H2H 실제 입력의 0.254125초 시차를 정렬해 두 영상 모두
259프레임·8.729259초로 저장했고 재측정 시차는 0초였습니다.
제공된 music_sync 테스트 4개는 30초 합성 녹음으로 실행했습니다.
양방향 시작 시차, 원본 해상도/배경 FPS, 무음·비일치 처리, 캐시 재사용을 검사했습니다.
노트북의 준비 이후 코드 셀 17개는 모델 호출을 대체한 CPU 연결 검사로 실행했습니다.
GPU 모델 전체 추론을 새로 실행한 검증은 아닙니다.
기록: `work/music_sync_integration_20260915_002154/`.

## 기존 처리 흐름

`run_enhancement.ipynb`의 춤 보정, SVOR, 자동 배치, 원본 B 복원,
전경 합성, 자동 조명 흐름을 복사했습니다. 결과/캐시 이름은 run_depth로
분리하고 B·C 가림 판단만 Video Depth Anything Large로 교체했습니다.
기존 노트북/가림 알고리즘은 변경하지 않습니다.

## 실행

- `run_depth.ipynb`를 Python (video-layer) 커널로 처음부터 실행합니다.
- E-4에서 원본 배경 전체의 깊이를 추론합니다. 선택 GPU는 기존 셀 설정을
  따릅니다. 조명·SVOR 모델과 동시에 GPU에 상주시키지 않습니다.
- 모델: `vendor/Video-Depth-Anything/checkpoints/video_depth_anything_vitl.pth`.
- 런타임: 기존 video-layer Python/PyTorch. 추가 의존성 easydict 1.13만
  `.model-envs/video-depth-deps`에 설치했습니다. 기존 환경 패키지는 바꾸지 않았습니다.
- xFormers 바이너리 설치 대신 PyTorch SDPA를 사용합니다.
- 시간축 attention의 공간 위치·헤드 묶음은 최대 8,192행씩 나눕니다.
  세로 영상에서 CUDA 배치/grid 제한을 넘지 않게 하며, 각 행의 전체
  시간축과 영상 해상도는 그대로 유지합니다.
- GPU 로그와 공유 깊이 캐시: `work/video_depth_anything/<signature>/`.
- 가림 마스크/프레임별 진단: `work/depth_occlusion/<signature>/occlusion.json`.
- E-4·마지막 비교 영상·자동 조명 최종 결과에 원본 `BG_SRC`의 소리를 넣습니다.
  비교 영상에는 소리 한 트랙만 사용하며, 오디오가 짧아도 영상은 자르지 않습니다.
- 다운로드 버전, SHA256 및 검증 기록: `work/depth_setup/setup.json`.

## 깊이를 C에 적용하는 방식

1. A와 B가 함께 있는 제거 전 원본을 원래 프레임/FPS 그대로 분석합니다.
   상대 역깊이 값이 클수록 카메라에 가깝습니다. 영상별 정규화된 컬러
   시각화나 독립적으로 추론한 C 영상의 깊이를 비교하지 않습니다.
2. 원본 A 마스크 안쪽에서 머리·몸통·좌우 위팔/아래팔·허벅지/종아리의
   깊이 중앙값을 구합니다. A·C 관절의 0.2초 이하 내부 누락은 앞뒤 관측으로
   보간하고, 긴 누락의 시작은 최대 0.2초만 몸 이동을 따라 유지합니다.
   신뢰할 수 있는 관절·깊이 관측이 계속 없으면 미확인으로 둡니다.
3. C의 실제 합성 위치/스케일에 관절을 놓고 대응 부위에 A의 깊이를 전달합니다.
   신체 크기에 비례한 각 부위 주변 영역만 후보로 삼아 발을 멀리 있는 팔에
   배정하지 않습니다. 이전 부위 마스크를 관절 움직임에 맞춰 대응해 애매한
   경계에서 부위가 바뀌는 것을 줄입니다. 명확히 가까운 새 부위는 반영합니다.
   춤 보정의 미러 선택에 따라 좌우 부위의 깊이 대응을 바꿉니다.
4. B·C 겹침에서 B의 역깊이와 전달된 C 부위 깊이를 비교합니다. 깊이 차이가
   불확실하면 최대 0.2초 동안 부위의 이전 판단을 유지합니다. 불확실성으로
   정규화한 최근 3프레임 깊이 차이의 중앙값으로 일시적인 반전을 억제합니다.
   반대 판단은 필터링 후 두 프레임 연속 근거가 있어야 전환합니다.
   지속적인 실제 교차는 통상 3프레임 이내에 반영됩니다. 오래 불명확하면 기본 C 합성을
   유지하고 unknown_pixels에 기록합니다. 발 높이나 원본 경계 기반 앞뒤
   판단으로 우회하지 않습니다.
5. B가 앞인 현재 겹침 픽셀만 원본 B로 복원하고 C 알파에서 제외합니다.
   가림 마스크 경계만 3×3 커널(반경 1픽셀)로 완화하고 현재 B·C 겹침 밖은
   반드시 0으로 제한합니다. C 내부 RGB에는 블러를 적용하지 않습니다.
   기존 Renderer는 이 마스크의 적용에만 사용하며 앞뒤를 추정하지 않습니다.
6. 마지막 비교 셀은 보정 전 C의 관절도 별도로 분석합니다. 깊이 캐시는
   공유하지만 전·후 가림 마스크는 각각 생성합니다. 이 최초 관절 분석은
   CPU 추가 시간이 필요하며 이후 재실행에서는 캐시를 사용합니다.

후처리 v2 수정 후 기존 커널에서는 E-4와 마지막 비교 셀을 재실행합니다.
E-4가 모듈을 다시 불러오며, 코드 해시 변경으로 가림 마스크만 새로 생성합니다.
깊이 모델·입력·깊이 worker가 같으면 기존 깊이 캐시를 그대로 재사용합니다.

이는 관측된 A의 **부위별 깊이 전달**이며, A의 완전한 3D 표면을 복원하거나
C의 숨겨진 자세 깊이를 정확하게 생성하는 방식은 아닙니다. 가까이 교차하는
손·팔, A가 완전히 가려진 부위, 마스크 오류에서는 앞뒤가 틀릴 수 있습니다.
부위 중앙값이므로 한 부위 내부의 세밀한 깊이 굴곡도 생략됩니다.

## 검증 범위

공식 체크포인트 해시/strict 로딩, CPU의 32프레임 소형 입력 순전파,
부위 대응·미러·깊이 부호·시간축 전환·노트북 구문을 검사했습니다.
이번 검증에서는 GPU 전체 추론을 새로 실행하지 않았습니다.
이 검증은 프로젝트 규칙에 따라 지정된 video-layer Python과 CPU로 수행했습니다.

후처리 v2는 저장된 AESPA 영상의 깊이·관절·전경으로 190프레임 전체를
CPU 재처리했습니다. 159~162프레임의 발 겹침이 모두 정강이로 대응되고
B 뒤에 유지되는 것을 확인했습니다. 짧은 관절 누락/장기 누락 만료,
먼 부위 배정 거부, 이동하는 부위 대응, 지속적인 실제 앞뒤 전환,
1픽셀 경계와 겹침 밖 불변, 출력 프레임·FPS·크기도 검사했습니다.
후처리 생성은 캐시 검증을 포함해 약 18.8초, 합성 및 전후 비교 저장은
약 17.9초였습니다. 모델 추론 시간이나 수정 전 대비 추가 시간은 아닙니다.
검사 코드·기록: `work/depth_setup/flicker_fix_20260914/`.
이는 특정 깜빡임 수정 검증이며 모든 가림 판단의 정답률을 측정한 결과는 아닙니다.

공식 코드: https://github.com/DepthAnything/Video-Depth-Anything

## 춤·배치 흔들림 개선 (2026-09-15)

새 춤 보정은 `correction-v6`, 자동 배치는 `anatomical-consensus-contact-v5`입니다.
몸통·허벅지·종아리에 공통으로 나타나는 크기 변화만 완만하게 반영합니다.
인물 전체를 삼각형으로 휘게 하던 보정을 팔·다리 주변의 제한된 변형으로
교체하고, 짧은 관절 누락·시점 불일치·오래 보이지 않는 관절을 보수적으로 처리합니다.
실제 마스크에서 관측한 신발 바닥 높이를 활용하고, 발이 계속 잘린 영상은
공통 골반 또는 목을 기준으로 배치합니다.

기존 커널 상태가 있다면 파일을 다시 열어 D-3 → D-4 → E-4 → 마지막 비교 셀을
실행합니다. E-3은 선택 미리보기입니다. D-3은 v5 작업을 새 폴더로 옮기며
저장된 자세를 재사용합니다. 새 전경에 대한 배치 관절 분석은 필요할 수 있으나,
같은 원본의 SVOR 및 Video Depth Anything 추론을 다시 할 필요는 없습니다.
마지막 비교 셀의 양쪽에는 모두 새 배치 안정화가 들어갑니다.

추가 환경 설치는 필요 없습니다. 상세 분석과 CPU 검증 범위는
[DANCE_STABILITY.md](DANCE_STABILITY.md)에 기록했습니다.

## 배치 분석의 MP4 끝 프레임 누락 수정 (2026-09-15)

NMIXX 음악 정렬 출력은 OpenCV 5에서는 175프레임, 별도 FFmpeg 디코더에서는
173프레임이 읽혔습니다. 음악 정렬의 FPS 필터에 긴 소수 문자열을 넘기면서
매우 큰 분모/시간 기준을 가진 MP4가 만들어지는 호환성 문제였습니다.
FPS를 분모가 제한된 유리수로 저장하자 동일 입력의 새 출력은 두 디코더에서
모두 175프레임으로 읽혔고 FPS·길이·해상도·오디오를 유지했습니다.

배치 관절 worker는 MP4를 별도 OpenCV 환경에서 다시 디코딩하지 않습니다.
노트북 환경에서 원본을 PNG로 읽고 실제 프레임 수·해상도를 검사한 뒤 전달합니다.
원본 해시·디코더 버전·PNG 해시로 검증한 프레임은 work 아래에서 재사용합니다.
정말로 프레임 수가 다르면 관절 모델을 실행하기 전에 예상/실제 수를 표시하며
마지막 프레임을 임의로 복제하지 않습니다. 기존 영상 파일·추적·춤 보정 결과는
변경하지 않았으므로 실패한 E-3부터 재실행하면 됩니다.

검증: 지정된 video-layer Python으로 실제 175프레임의 PNG 전달 및 worker
입출력을 확인했습니다(관절 모델은 대체). 새로운 음악 정렬 영상은 OpenCV와
별도 FFprobe로 전부 읽었습니다. GPU 추론·설치·다운로드는 실행하지 않았습니다.
기록: `work/depth_setup/decode_fix_20260915_091319_93b6c4d7/validation.json`.
