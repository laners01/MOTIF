## 1. 사전계산 경로 개편 — sha256 → challenge/participant seq (`ab6d48d`)

### 배경 / 계약
백엔드가 CHALLENGE base 영상을 `private/edited/{challengeSeq}/{participantSeq}/{uuid}.mp4`에 두고, 그에 대응하는 사전계산은 **같은 seq 경로** `precomputed/{c}/{p}/` 아래에 있어야 한다고 요구.

### 변경 (`s3_storage.py`)
- 기존: `precomputed/{sha256(base_video_key)}/…` (해시 폴더)
- 변경: `_precomputed_dir()`가 정규식 `(?:^|/)edited/(\d+)/(\d+)/[^/]+$`로 base_video_key에서 `(c,p)`를 파싱 → `precomputed/{c}/{p}/…`. 형식 불일치 시 **즉시 `ValueError`**(조용한 오폴더 방지, 신뢰 경계).
- `precomputed_manifest_key`/`precomputed_artifact_key`가 이 함수를 공유 → **precompute(writer)·compose(reader) 동시 전환**.
- `{c}`/`{p}`는 자릿수 제한 없음(임의 양의 정수).

### 선택 근거
A안(base_video_key 파싱) 채택: 백엔드 변경 0, `base_video_key`가 이미 (c,p)를 담아 단일 진실원천, 백엔드가 계약으로 못박은 `edited/{c}/{p}/` 규칙에만 결합. (B안=요청에 seq 필드 추가는 이중 원천 위험으로 기각.)

### 소비 레이아웃 (compose가 `precomputed/{c}/{p}/`에서 찾는 것)
```
precomputed/{c}/{p}/
├── ready.json                    # 매니페스트/포인터
└── artifacts/{content_sha256}.tar.gz   # 포터블 패키지(ready.json의 artifact_key가 가리킴)
```
`ready.json` 필수 필드: `status="ready"`, `portable_format="portable-precomputed-v1"`, `base_video_key`(요청과 완전일치), `artifact_key`, `artifact_sha256`, `package_path`, `background_sha256`, `implementation`(지문), `model_bundle_version`, `people`.

### 공유 규칙
같은 `(challenge, slot)`(= 같은 base_video_key) 요청은 **같은 precomputed 재사용**. 같은 챌린지라도 슬롯이 다르면 base가 달라 별도 폴더. compose는 base_video_key만으로 위치를 결정론적으로 도출(유저 raw는 조회에 미사용) → precompute 1회 ↔ compose N회.

## 2. MOTIF 합성 통합 (`5177972`)

### 개념 (CHALLENGE와 별개)
- **MOTIF**: 구매 에셋 배경(read-only) 위에 유저 촬영본에서 **한 사람만 추출**해 **조명만** 맞춰 얹는 합성. **precompute 없음, 제거(SVOR/인페인팅) 없음, 춤보정·기하·그림자·좌우반전 없음.**
- CHALLENGE와 달리 **1개 잡(compose 분기)** 으로 자기완결.

### 구조
- `source/util/motif_composite.py`: 검증된 노트북 모듈 **바이트 동일 이식**(핵심 로직 무수정). `prepare`(RF-DETR/SAM2 유저추적 → contain 배치 → edge matte → RelightVid 입력준비) / `finish`(RelightVid 20-step → 조명적용 → 원본배경 합성 → 배경 오디오 MP4) 두 서브프로세스.
- `runtime.py`: `motif` 모듈을 runtime 네임스페이스에 노출(GPU 잡 기동 시에만 import).
- `service.py`: `process_video`가 `job_type`으로 분기 → `process_challenge`(기존 본문 무수정, 이름만 변경) / `process_motif`(신규).

### MOTIF S3 I/O (요청 필드 verbatim, prefix 하드코딩 없음)
```
유저  : raw_video_key  (raw/{job_uuid}.mp4)     → download → work/.../inputs/foreground.mp4
에셋  : base_video_key (assets/{uuid}.mp4)      → download → work/.../inputs/background.mp4
처리  : motif.prepare(bg, fg, gpu=runtime.gpu) → motif.finish(session)
검증  : 출력 길이 == base_duration_ms ±0.5s (재인코딩 없음, 품질 보존)
결과  : final.mp4 → upload → output_video_key (results/motif/{job_uuid}.mp4)
반환  : worker.run_job이 ProcessResponse→client.done, 예외→client.failed (CHALLENGE와 동일 경로)
```
- MOTIF 분기는 `precomputed_manifest_key`/`_read_json(READY)`/`_choose_people` 등 **precompute 경로를 일절 호출 안 함**(유닛테스트로 못박음). base가 `assets/…`라 seq 파서에도 안 닿음.
- v0.5 스키마가 이미 MOTIF 수용: `slot: Slot|None`, CHALLENGE만 slot 강제. MOTIF는 `slot:null`.
- 에러 매핑: 기존 `_fail_code`가 이미 커버(사람 못 찾음→PERSON_NOT_DETECTED, S3 404→INPUT_NOT_FOUND, 업로드 실패→UPLOAD_FAILED, CUDA→GPU_ERROR). worker 무변경.

### 과거 트러블 재발 점검 (전부 안전)
| 과거 이슈 | MOTIF 경로 | 상태 |
|---|---|---|
| gcsfuse mmap 느린 로딩 | RelightVid=`variant_worker.py`(순차-read 패치본) 재사용, SVOR 미사용, RF-DETR/SAM2는 torch.load(순차) ~2분 | 안전 |
| emptyDir 교차볼륨 EXDEV(Errno18) | `variants.finish`는 이미 `shutil.move`. 최종 인코딩 `encode_frames`→`add_audio`는 ffmpeg가 `output/`에 직접 write(rename 아님) | 안전 |
| read-only 레이어 makedirs(Errno30) | 같은 RelightVid vendor(guard 픽스). 자기 산출물은 work/·output/·video/downloads/ | 안전 |
| 60분 타임아웃 | MOTIF ≈ 12–14분(스모크 실측 14m7s) | 여유 |

## 3. intake 503 전량 거절 장애 복구 (2026-09-22) + `e132532`

### 증상
백엔드가 `/submit`으로 접수한 잡 전량 **503**(202 0건). GET엔 http.server 기본 501 → 서비스는 살아 있고 do_POST가 503을 내는 상황.

### 근본 원인 (우리쪽 설정)
intake env `COMPOSE_JOB_RESOURCE`/`PRECOMPUTE_JOB_RESOURCE`가 **`locations/asia-southeast1/…`**(intake 자기 리전)을 가리켰으나 GPU 잡은 **`us-central1`**에 존재 → `run.googleapis.com/v2/{job}:run`이 **404** → intake의 launch-실패 except가 503 반환. (403이 아니므로 SA 권한·토큰은 정상. v0.5 파싱도 정상 — 검증 통과 후 실행 단계에서 실패.)

### 조치
1. **긴급 복구**: intake env를 `us-central1`로 교정(rev 00003) → 즉시 202 정상화. **URL·리전 불변** → 백엔드 호출 방식 변경 불필요(그냥 재시도).
2. **검증 실패 → 400 분리** (`intake.py`): 본문 검증 실패(ValueError/JSONDecodeError)를 503→**400**(영구 오류, 재시도 무의미). 잡 실행 실패만 **503** 유지(재시도 신호). intake v3(rev 00004).
3. **재발 방지**: `07-deployment-notes-2026-09-20.md`의 JOB_RESOURCE 리전을 us-central1로 교정 + "Job=us-central1 / intake=asia-southeast1 분리" 경고 명시.

### 백엔드 영향
- 호출 방식/URL 그대로. 응답만 503→202로 정상화. 앞으로 본문 오류는 400(재시도 대상 아님).
- precompute→compose 순서 유지.

## 5. CHALLENGE compose 소비 실패 진단·수정 (`98402e0`, v28)

intake 503 복구 후 백엔드 재시도 CHALLENGE 잡들이 **접수(202)는 되나 초반에 빠르게 실패**. 워커가 예외를 잡아 `client.failed`(백엔드 실패 통보) 후 **exit 0** → 콘솔은 succeeded=1로 오해 유발("콘솔 성공 ≠ 합성 성공", exit-code 의미론).

두 가지 서로 다른 원인:
1. **미존재 (c,p) → `NoSuchKey`**: 예) `5c7c6fc4`가 `private/edited/34/35/…` 요청 → `precomputed/34/35/ready.json` 없음(보유 쌍은 1/1~18/19 불규칙). **백엔드가 그 챌린지/슬롯 precompute를 선행해야 하는 데이터 공백**(코드 문제 아님).
2. **`verify_package` 파일목록 불일치**: 예) `1056a6d4`가 `14/15`(`precomputed_예지_채령`) 소비 → ready.json은 정상(portable-precomputed-v1, base 일치, model_bundle_version 일치)인데 tar 내부 파일집합 ≠ manifest.files.
   - **정밀 진단**(1.6GB 패키지 로컬 재현): tar 2979 vs manifest.files 2978, **초과 1개 = `.ipynb_checkpoints/source-checkpoint.mp4`**(누락 0). 노트북 export 시 딸려온 주피터 자동저장 잔재.
   - **`MOTIF_SKIP_FINGERPRINT`로는 안 풀림** — 그 플래그는 `implementation` 지문만 우회, 파일 무결성(verify_package)은 별개.

**수정**: `precomputed_export.verify_package`가 `.ipynb_checkpoints/` 하위 파일을 무결성 대조에서 제외(한 줄). 실데이터는 여전히 per-file SHA-256 검증. **재분석/재업로드 불요** — 기존 S3 데이터 그대로 소비. 로컬 재현으로 14/15 불일치 해소 확인(2978==2978). v28 빌드·두 잡 전환 완료.
- ⚠️ 14/15 기준 검증. 다른 패키지에 `.ipynb_checkpoints/` 외 잔재가 있으면 또 걸릴 수 있음. 근본책은 AI팀이 export 전 분석 dir 청소.

### 5.1 제거 대상 인물 선택 KeyError → anchor 선택 제거 (`0909888` v29 미배포 → `0907ad9` v30)

v28로 verify_package를 통과해 `run_post`까지 진입한 뒤 **`KeyError: 'background_frames'`**(prepost.py:407 materialize_segment)로 실패.
- **원인**: `_choose_people`가 요청 `slot.anchor` 최근접으로 제거 대상을 골랐는데, 고정 단일-제거 패키지는 **`background_frames` 보유 인물이 1명뿐**. 게다가 요청 anchor(썸네일 기준, y≈0.27)와 패키지 people anchor(소스 프레임, y≈0.96)가 **좌표계 불일치** → driver(id=2)를 제거로 오선택 → `asset['people']['2']['background_frames']` 접근 실패.
  - 실측(xm2s6, base=`private/edited/14/15/…`, anchor(0.3463,0.271)): x는 제거대상 id=1과 거의 일치했으나 y 불일치가 거리 지표를 뒤집어 id=2 선택.
- **핵심**: anchor는 `_choose_people`(인물 선택)에만 쓰이고 `run_post`(배치)에는 전달되지 않음 → **유저 합성 위치와 무관**. 위치는 제거된 인물의 사전계산 geometry가 결정.
- **수정 경위**:
  - v29(`0909888`, **미배포**): removable 후보를 `background_frames` 보유자로 제한 + 단일이면 anchor 무관 강제, 다중이면 anchor 폴백.
  - v30(`0907ad9`): **anchor 선택 자체를 제거**. 항상 `background_frames` 보유자(정확히 1명)를 제거, 0명/2명이면 계약 위반으로 거부. `_selected_slot`·anchor 거리 코드 삭제. (이 데이터엔 anchor 기반 disambiguation이 애초에 불필요.)
- **상태**: **v30 배포 완료(compose/precompute 전환됨, 2026-09-23).** 제거 대상 background_frames 선택이 라이브.

## 9. A — `correction.apply()` 프레임 루프 프로세스 병렬화 (승인 2026-09-23 · 커밋 `3d56f0d` · v31 배포 · 실측 §9.5)

### 9.1 설계 (`source/enhancement/correction.py`)
- 루프 본문을 **그대로** `_render_frames(render,work,indices,base,selected,sampled_pose,offsets,n,*,cv_threads)`로 추출(수식 무변경, 파일명은 절대 인덱스 i, `j`→`selected[k]`).
- `_render_all(...)`: `MOTIF_CORRECTION_WORKERS`(기본 `min(18, vCPU-1)`; **`=1`이면 기존 직렬 경로와 완전 동일** — 롤백·A/B 스위치) → `np.array_split`로 **연속 청크**(FrameSampler 인접쌍 캐시 유지) → `ProcessPoolExecutor(mp_context=spawn)`, 청크 완료마다 `프레임 보정 done/n`.
- 완화책: **spawn**(부모 `correction_worker`가 ORT CUDA 세션 보유 → fork 데드락 회피), 워커 `cv2.setNumThreads(1)` + `OMP/OPENBLAS/MKL_NUM_THREADS=1`(과다구독 방지), `n<2*workers`면 직렬. 자식 import 체인(cv2/numpy/scipy/removal_experiments/model_test/temporal)에 torch 없음 → 워커 기동 1~2초.

**해석**: 절감은 예측한 두 항목에서만 나왔고(#1 −669s, #3 GVHMR분 −82s) 나머지 단계는 ±1~2%(노드 편차) → 부수효과 없음. 남은 큰 덩어리는 RelightVid 디노이징 ~400s(step=품질, 불가)·검출·추적 250s(SAM2 setup ~106 + 추적)·GVHMR 추론 ~150s·init ~92s. 후보 #2·#3(메인)·#4·#5(§8.5)를 다 해도 ≈2~4분 → **~22~24분이 현 구조의 바닥**.

## 10. CHALLENGE 다중 인물 검출 거부 → 최고 신뢰도 자동 선택 (커밋 `2d6f681` · v32 배포)

### 증상
유저 raw 업로드가 `MULTIPLE_PERSONS`로 실패. 실패 실행 `8vb2c`(job_uuid `52468054…`, base `edited/14/15`) 로그:
```
자동 검출: frame 0, 사람 4명 (id1=0.95, id2=0.73, id3=0.66, id4=0.65) · 기본 선택 id1
prepost.py line 463: if len(ids)>1: raise ValueError('유저 영상에서 여러 사람을 찾았습니다.')
```
사용자 확인 결과 영상 시작(frame 0) 배경에 실제로 여러 명이 함께 잡힘. id1=0.95가 유저 본인.

### 근본 원인
- `find_people`(rfdetr_person_detector.py)는 "인원 최다 프레임"을 앵커로 잡아 그 프레임의 사람 **전원**을 신뢰도 내림차순(id1=최고)으로 등록 → frame 0에 4명이면 `object_ids=[1,2,3,4]`.
- `prepost.postprocess`(challenge 경로)는 `if len(ids)>1: raise` 로 **무조건 거부**. 그러나 검출기는 이미 id1을 최고 신뢰도로 정렬하고, **MOTIF 경로(`motif_composite.py:200`)와 README 문서는 "여러 명이면 신뢰도 첫 인물 사용"**으로 명시 → 경로 간 정책 불일치.
- 앵커가 최다-인원 프레임이라, 24샘플 중 한 프레임에만 배경 인물/오탐이 있어도 job 전체가 거부되는 취약성.

### 수정 (`prepost.py`, +3/−1)
거부 가드를 제거해 기존 `cfg['foreground_id']=ids[0]`(=id1) 자동 선택으로 낙하:
- 1명일 때 동작 불변, 요청 `foreground_id` 지정 시 검증도 그대로.
- 다중 검출 시 로그 한 줄(`유저 영상에서 N명 검출 · 최고 신뢰도 ID … 자동 선택`)로 관제/디버깅에 자동 선택 사실 기록.
- **핵심 보정/합성 수식 무변경, 인물 선택 정책만 MOTIF 경로·문서와 일치**(CLAUDE.md 준수).
- `worker.py`의 `MULTIPLE_PERSONS` 매핑은 test_server가 참조하므로 유지(무해·사실상 dead).
